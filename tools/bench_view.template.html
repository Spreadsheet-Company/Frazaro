Viewport Renderer Benchmark

This page measures two ways of drawing a spreadsheet viewport, a canvas renderer and a virtualized DOM renderer, over the same records in the same windows, and how each one scales with the text it draws: the main-thread cost of a first draw, of 120 scroll steps of three rows, and of 20 steps of a whole window, at the protocol's two windows over a sparse record and then at full screen over a dense record down a ladder of four cell sizes. It is an engineering measurement of the browser's drawing, not a measurement of a person. The records it draws from are real frazaro view records of two synthetic programs, the lines the door printed, embedded in this file. The full-screen rows are honest only when the run happens in fullscreen: a browser culls the painting of what lies outside its viewport, so a full-screen case in a smaller window measures less than it draws. The page runs once on opening; press Fullscreen to enter it and run again, Run to run again; Copy takes the table.

How each number is measured
  • the records: the sparse record is the protocol's program, one cell a row (A with values on the odd rows, B with formulas on the even rows); the dense record fills every cell of R rows by C columns, values and formulas in alternate columns, so that a full-screen window is full of text.
  • cells with text: the non-empty cells of the record inside the window at the top of the sheet, rows 1 to R and columns 1 to C: the load drawn. The DOM renderer keeps R x C cell elements and writes the text of a row only when that row is recycled; the canvas renderer draws the cells with text again on every draw.
  • a draw's cost on the main thread: every draw starts at the top of an animation frame's callback phase (the harness awaits a frame before taking the clock), and its cost is the time from before the call to a task queued after the frame's rendering (a 0 ms timer, which runs once the frame's style, layout and paint recording are done), so the DOM's layout and paint recording count as the canvas's fill calls do, and a draw that keeps up reads its true cost and not the frame interval. Rasterization and compositing happen off the main thread and are not in the number; a frame they delay shows as dropped.
  • first draw ms: the first draw's cost so measured: the elements made or the canvas drawn, laid out and recorded.
  • step p50, p95 ms: 120 steps of 3 rows each from the top (12 in smoke mode); each step sets scrollTop, calls onScroll() synchronously, and is measured as above; nearest-rank percentiles over the steps. For the DOM renderer a 3-row step recycles three rows; for the canvas it is a full draw.
  • page p95 ms: 20 steps of a whole window of rows (2 in smoke mode), alternating between the top and the middle of the sheet, so that every page step is a full rewrite for both renderers, the DOM's worst path and the path a dragged scrollbar or a held Page Down takes.
  • max ms: the largest cost over the steps and the page steps.
  • sync p50 ms: the synchronous part of a step alone, the script's own work before the browser lays out or paints; the gap to the main-thread cost is what the browser does for the DOM renderer after the script returns.
  • dropped of N: how many of the N steps and page steps were followed by an animation frame later than one and a half times the display's own frame interval, which the page measures before the first measured case over thirty idle animation frames (the median delta between consecutive timestamps) and prints in the environment line.
  • holds the frame: yes when no step was dropped and both the step p95 and the page p95 are under one frame interval, the protocol's amended bar (docs/PROTOCOL.md section 8.1, amended 2026-10-08).
  • the ladder: the cell sizes 20 x 96, 16 x 80, 12 x 64 and 10 x 48 px (row height by column width, with 13, 11, 9 and 7 px text), each at full screen: as many whole rows as fit under the column headers and as many whole columns as fit beside the row headers and the scrollbar, in a container sized to the screen in CSS px. The normal window is 40 rows by 15 columns at 20 x 96. The slope and the capacity below the table are least-squares fits of the step p50 and the page p95 against the cells with text over the dense full-screen cases; the capacity is the load at which the fitted cost reaches one frame interval.
  • the order: one discarded warm-up case of each renderer first, at a small window with five scroll steps, so that the first measured case does not pay the page's one-time costs; then the frame interval; then the twelve measured cases in the table's order, the renderers alternating.
  • the door line: the time the door took to print each record, as tools/bench_view.ps1 measured it around the call.
