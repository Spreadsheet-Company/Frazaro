## THE DEPARTMENTS

Fortifications · Environment · Assurance · Optimization · VLA · Performance
Reviewer profile: compiler engineer. Done means: pinned, measured, reproducible.

### 🗣 THE LANGUAGE — *"What can be said, and does it keep meaning what it meant?"*
Linguistics · Compatibility · Grammar
Reviewer profile: linguist / domain expert who has lived in spreadsheets.
Done means: auditioned, proven, and promised. **This department is the moat.**

### 🪟 THE PRODUCT — *"Can a human find it, use it, install it?"*

### 🌍 THE COMMONS — *"Can others join, extend, and coexist?"*
Documentation · Governance · Interoperability
Reviewer profile: maintainer. Done means: someone else did it without asking.

### 🧑 THE PATIENT — *"Is anyone actually being helped, this week?"*
Pilot · SOP Import · Acquisition · Gap reporting
Reviewer profile: the user, who has not read this document and never will.
Done means: their SOP ran on their machine, on a Monday, without you in the room.

### 🛡 THE ADVERSARY — *"What can a hostile author, a hostile program, or a hostile input do?"*
Security
Reviewer profile: someone trying to break it — a profile no other department seats.
Done means: a threat model exists, the reachable object-model surface is default-deny,
and a phrasebook cannot act beyond it without visible, revocable consent.

Reviewer profile: the person who signs the form — the other reader no department here

# 🛡 ADVERSARY · SECURITY

*specimens: 1 — an audit finding, not a live exploit: this session's own read of `VLA_Interpreter.bas`/`VLA.bas` found `Application` plausibly reachable through the `CallByName` fallback with no capability gate, and `raw` splicing arbitrary VBA with no consent. Flagged for a live test, not yet confirmed as exploited — the same honesty this file already holds `AS.8`'s heuristics and `IN.11`'s parity claims to. This tranche exists because no department above ever seated a reader whose job was to look for this.*

- ✅ **SEC.0 — the threat model, written down.** Owner-reviewed (`docs/THREAT_MODEL.md`) and committed. What a program may reach; what a phrasebook may reach; who is trusted at each layer (base corpus, org phrasebook, community phrasebook, `raw`-bearing rule); what "zero-trust runtime" (IN.9's own phrase) actually promises today versus what an IT reviewer will assume it promises. *Why now:* every other item in this tranche cites it, and it costs a document, not a feature. Written against real code, not the roadmap's own secondhand description of it: confirmed by reading `VLA_Interpreter.bas`/`VLA.bas` directly — the `CallByName` fallback (§1.2) is a heuristic with no allowlist/denylist, confirmed reachable via `Application`'s own already-enumerated bare-dotted-globals; `Application.Run` against `VLA_Runtime.bas` (§1.3) turned out narrower than it first looks, since the module prefix is hardcoded, never user-derived; `raw` (§1.4) splices its own string content verbatim into the emitted module with zero validation, confirmed at the exact `VLA.bas` line. The single most load-bearing finding: "zero-trust runtime" means "needs no VBProject Trust Center prompt," not the modern zero-trust security sense an IT reviewer will assume — named as the gap most likely to matter in a real procurement conversation. *Pays into:* every `SEC.*` item below, `EN.1`'s capability probe, `DI.1`'s trust-prompt precedent. `~hours`

- ✅ **SEC.1 — capability gating of dynamic dispatch (Tier 0 + Tier 2 only).** Built and owner-verified live (`VLA_SELF-TESTS` pure 947/947, host 143/143; `VerifyReports` emitter 141/141, interpreter 141/141) and committed. The `CallByName` fallback in `DynamicGet`/`DynamicCall`/`DynamicSet` is removed from shipped builds; a 25-member census (not just G-TABLES — plain cell-`.value` reads and cross-sheet `.range` lookups too) was promoted to native `Select Case` arms first, closed by subtraction second. Tier 1 (permissioned/declared capabilities like `vlasendmail`) is scoped separately as `SEC.7`, not part of this item's own completion. *(more: BETA_ROADMAP1.md)*

- ✅ **SEC.2 — `raw` behind explicit, per-phrasebook consent.** Built and owner-verified live (VLA_SELF-TESTS pure 936/936, host 143/143; full manual click-through including a compiled `raw` statement actually executing). A phrasebook using `raw` shows a modal, naming the phrasebook, before its rules become reachable — not a new interaction pattern, the existing VBProject-trust one pointed at a second question. Gated at `EnglishLoadVocabulary` (the file-path loader), not `EnglishLoadVocabularyText` — that shared primitive is what `VLA_Browser.bas`'s already-shipped, host-free translate API calls directly, documented as never showing a dialog; a first draft that gated there only *appeared* clean under `check_translate_purity.ps1` on a technicality. Two remembered scopes offered as an explicit choice, not a silent default: this workbook only, or every workbook on this device (named trade-offs, not a free convenience) — see BETA_ROADMAP1.md's own SEC.2 entry for the full mechanism, the workbook-scope/`ActiveWorkbook` correctness fix, and the VBA declarations-block lesson found along the way. *(more: BETA_ROADMAP1.md)* *Why now:* `raw` is the one form no future static analysis will ever be able to reason about, by design (F.2's own text: "usable directly ... no macro required" for `quote`, and `raw` is `quote`'s opposite — opaque, not self-contained data). *Depends on:* SEC.0. `~days`

- ⬜ **SEC.3 — phrasebook provenance for capability-requiring effects.** Which *layer* — base corpus, org phrasebook, community phrasebook — introduced a given `raw` splice or mail-send, attached to the emitted code itself, not just to a load-time log line. Extends `LISTOPS-PROVENANCE`'s existing `gen-row`/`at-row` tagging by one field rather than building new machinery: that mechanism already answers "which table row produced this rule"; the same answers "which trust layer authorized this effect." *Why now:* GO.3 already names the phrasebook registry "a supply chain" with no mechanism; this is the mechanism, and it turns "who do I hold accountable for this effect" from an investigation into a lookup. *Depends on:* SEC.1's tiers existing to have something worth attributing. `~days`

- ✅ **SEC.4 — formula/CSV-injection guard.** Owner-tested live (`VLA_SELF-TESTS` pure 903/903, host 119/119, plus a live cell check — `Put "=SUM(A1:A2)" into cell B1.` — confirming the neutralized apostrophe shows correctly in the formula bar with no stray visible character in the cell itself, the one real uncertainty this item's own build could not resolve without a live Excel session) and committed. A program-written cell value beginning with `=` becomes a live formula; nothing sanitized it before this pass — the same class of bug CSV-export tooling has been bitten by industry-wide for a decade. *Why now:* concrete, scoped, and cheap; a single guard at the runtime helper that writes cell values. Confirmed against real code, not assumed: `DynamicSet`'s own `Case "value"` (`VLA_Interpreter.bas`) is the ONLY `.Value`-writing site in the whole codebase — every `Put X into cell Y`-shaped sentence routes through it. **Built as `NeutralizeFormulaInjection`, new, `VLA_Interpreter.bas`:** guards all four OWASP-named trigger characters (`=`/`+`/`-`/`@`), not just the roadmap's own illustrative `=` — leaving the other three out would be an incomplete fix for the class of bug this item names, not a narrower one. Neutralized (a leading apostrophe, forcing Excel's own text interpretation), never refused: a computed value legitimately starting with one of these — an imported note, a negative-number-as-text field, an email address — is ordinary data, not an authoring mistake, and `Case "formula"` (the same `Select Case`, untouched) already covers the case where writing a live formula is genuinely the stated intent — a `Put formula "=B2*2" into cell B3.`-shaped sentence (`english.vla`'s own existing rule) routes through `Case "formula"` directly and is completely unaffected. Only `VarType vbString` is ever in scope; every other type (a real number, a Boolean) passes through untouched. Logged via the interpreter's own existing `LogEffect` whenever it actually fires, so a neutralization is auditable, never silent. Tests: `VLA_Tests.TestInterpreterCsvInjectionGuard` (pure — `NeutralizeFormulaInjection` made `Public` specifically so this needs no live host object, all four trigger characters, an ordinary string and an empty string both untouched, a trigger character NOT at the string's own start left alone, every non-string VarType untouched, and an object input passed through via `Set`, a regression pin for the exact "bare Variant assignment invokes an object's own default member" trap this session's own PROLOG work already hit more than once), wired into `VlaSelfTest`.

- ✅ **SEC.5 — `SECURITY.md` and a disclosure contact.** Owner-reviewed and committed (`docs/SECURITY.md`) — contact address (`english@spreadsheet.company`) and response commitment (3-business-day acknowledgment, no fixed remediation deadline, severity-prioritized, reporter kept informed) both filled in by the owner rather than guessed. A place a finder is told to report to, and a stated response commitment — the minimum credible artifact before any external pilot (`PI.*`) or public download. *Honest tension, named rather than solved here:* `SD-13`'s no-network stance means a disclosed vulnerability has no push-update path to the people already running an affected build; this item does not resolve that, it only makes sure a report has somewhere to land. `~hours`

- ⬜ **SEC.6 — a security review before wide release.** Gated on SEC.0–SEC.2 landing and live-tested. *Expiry condition, G9-shaped, now met:* the interpreter's default-runtime dispatch surface is default-deny (SEC.1) and `raw` is gated (SEC.2), both committed — unlocked, not itself done. Not gated on SEC.7. `~days`–`~weeks`

- ⬜ **SEC.7 — Tier 1: permissioned, declared capabilities.** The small set of verbs with real external effect — `vlasendmail` today; file I/O once G-FILES ships — each meant to carry a `requires: capability:<name>` tag, checked at load, refused in words when absent. Scoped, not built: build a minimal general `F.10` first (`requires:` generalized from grammar-version dependency to permission, one shared parser rather than two); reuse SEC.2's own two-scope consent UX, not DI.1's blanket per-publisher trust; build the requires:/consent machinery generically, not single-purpose to `vlasendmail`; check at phrasebook load time, matching SEC.2's own chokepoint. *Depends on:* SEC.1, F.10. *(more: BETA_ROADMAP1.md)* `~weeks`

# 🧑 PATIENT · SOP IMPORT

*The raw-material problem, not the sentence-grammar problem — SD-16 already settled how one sentence gets parsed, and this tranche's own owner-simplified design (this session) goes further than the pattern this file's other grammar-adjacent tooling usually takes: no triage heuristic of any kind runs before a line ever reaches the phrasebook — not even a sentence-blind one. A real SOP lives today in a Word document or a PDF, with inline screenshots and side-notes mixed into the numbered steps, and today there is no tooling between "raw document" and `PI.2`'s own hand-typed transcript at all. Named explicitly so it does not stay an implicit assumption inside `PI.2`/`PI.3`: this tranche is what makes THOSE items tractable for a real Word/PDF document instead of a pre-cleaned transcript; it does not replace them. specimens: 0 until PI.2 (LE.6/LE.7's own precedent — no specimen exists until a real transcript does).*

- ⬜ **SOP.1 — Word and PDF intake, via Word itself.** Owner call, this session, overriding this item's own earlier draft (plain-text-only, `.docx`/`.pdf` named a ceiling): a Word document is where a real SOP actually lives, and telling a prospective client "first retype your procedure as plain text" reads as a rewrite-from-scratch — the wrong first impression for a beta. Neither format gets a hand-built parser: both route through Word's own object model, automated via COM (`CreateObject("Word.Application")`) — the same "drive the real application, never reimplement its file format" instinct SD-1 already applies to VBA itself, extended here to "Word is a backend too, for reading its own files." A `.docx` opens directly; a `.pdf` opens through Word's own built-in PDF-to-Word conversion (a real, existing Word feature — Word reflows a PDF's own text into an editable document on open) — both formats end this step as an ordinary Word `Document` object, walked identically from there by `SOP.2`. Two real limits, named now rather than discovered live: this needs Word installed and automatable on the machine — refused by name, never crashed, when it isn't (`IO.2`'s own "refuse in words, name the reason — or switch backends" precedent, applied to a second application instead of a second VBA host); and Word's own PDF conversion reflows a BORN-DIGITAL text PDF but does not OCR a scanned or photocopied one — a scanned SOP converts to something with no recoverable text, a real ceiling, not a bug to chase later. Plain-text paste stays supported too, as the always-available fallback needing no external application at all. *Open question for whoever scopes this in detail, not resolved here:* whether automating Word crosses into SD-15's own "dynamic dispatch beyond the native, reviewed tier" territory, or stays tooling-side — the add-in's own authoring flow, not an emitted, user-facing capability, the same way the panel itself already isn't SD-15's concern — a real judgment call, not a rubber stamp. *Worth a name-check by 🛡 ADVERSARY, not solved here either:* opening an arbitrary user-supplied `.docx` for text extraction should never be confused with running it — a document carrying its own macros must never have them triggered by this path. `~days`–`~weeks`

- ⬜ **SOP.2 — one line in, one row out, no classification at all.** Owner-simplified, this session, replacing this item's own earlier line-kind-triage design outright: every extracted unit — a Word paragraph (`SOP.1`'s own walked `Document.Paragraphs`, one row each, the natural unit a numbered step already lives in) or a plain-text paste's own line (split on the ordinary line break, when no Word document is involved at all) — becomes exactly one row, completely unmodified, in written order. No attempt anywhere in this item to guess "is this an instruction, a comment, a header" — that judgment is left entirely to `SOP.4`'s own Verify pass and the human reading its result. One small, explicitly-decided exception, not a silent special case: a wholly blank paragraph/line is dropped rather than becoming an empty row, since an empty row carries no decision for a human to make either way. Deliberately the simplest possible design — SD-16's own spirit taken further than this project's other grammar-adjacent tooling usually goes, since not even a sentence-blind heuristic runs before a line reaches the phrasebook, only extraction and row-splitting. `~hours`

- ⬜ **SOP.3 — an embedded image becomes a `#`-prefixed comment line, in place.** The direct, concrete answer to "images aren't parsed": during the SAME walk `SOP.1`/`SOP.2` already do, an embedded picture found inside a paragraph (a Word `InlineShape`, confirm the exact anchoring `Document.Paragraphs` exposes before assuming the shape) is emitted as its OWN row, in its own document position, auto-numbered in encounter order — `# [image1]`, `# [image2]`, and so on — reusing `VLA`'s own existing leading-`;` comment-line convention's SIBLING marker (`#`, `SOP.4`'s own manual-marking convention below) rather than inventing a third. Never Verify-dependent and never a heuristic guess, unlike an ordinary text row: an image's own position is known structurally from the Word object model at extraction time, not inferred after the fact. OCR, computer vision, and "reading" a screenshot's own content are explicitly NOT bought here — named as this item's own ceiling, `LISPIMPORT`/`DIALECT-REGEN`'s own catalogue-not-a-chokepoint precedent for staying honestly bounded. *Why this matters more than it looks:* a step whose entire instruction was a screenshot, silently dropped, does not fail loudly — it just vanishes, the exact silent-loss failure mode `docs/AUDIT.md`'s own Part III (`U.18`'s own citation of it) exists to prevent, now one layer earlier than U.18's own per-run log. `~days`

- ⬜ **SOP.4 — Verify, then a hashtag, not a workbench.** Owner-simplified, this session, replacing this item's own earlier LE.7-loop-reuse design outright: every row `SOP.2`/`SOP.3` produced runs through Verify (the interpreter's own existing deterministic validate-and-refuse step) exactly as authored, with no drafting, no AI bridge, no candidate-sentence generation of any kind. A row that fails needs exactly one guided fix, named up front rather than left to be discovered by trial and error: the user prepends `#` to the line, turning it into an ordinary comment — the identical convention `SOP.3`'s own image markers already use, one convention for "this row is not a worksheet instruction," never two. A row may instead be hand-edited and re-run through Verify, for the case where the line genuinely IS an instruction, just not phrased the way the phrasebook currently recognizes it. This is `PI.3`'s own concierge run, made self-service: the corpus's own refusal is the ENTIRE guidance mechanism, doing the classification work `SOP.2` deliberately declined to do up front. *Depends on:* SOP.2, SOP.3, and Verify itself (the existing mechanism, not a new one). `~days`

- ⬜ **SOP.5 — the acceptance sentence, written before the run.** `PI.5`'s own kill-criteria discipline, pointed at this tranche specifically, decided now so success cannot be quietly redefined once something ships. Proposed: *a real SOP — a genuine Word document or PDF, containing at least one inline image and at least one side-comment with no `#` already on it — gets imported, run through Verify, and hand-marked or corrected line by line into a running Frazaro program, by the same named pilot user `PI.1` already committed to, without the owner hand-authoring any VBA outside the phrasebook.* If that sentence cannot be written truthfully after SOP.1–4 ship, the tranche is not done regardless of what got built. `~hours`

  **The scoping question, resolved, not deferred:** whether this is a `defmacro` or a real engine primitive turns out not to be a judgment call — it's forced. A `defmacro` in this system is parameter-substitution into a fixed template *form*, decided once at macro-definition time; it has no way to parse the *contents* of a string literal supplied at a call site and discover named or positional holes inside it, because that string is just one more argument value being substituted, never inspected. The only thing a `format` `defmacro` could honestly deliver is `&` under a new name — zero real capability gained for zero cost, not a cheap version of the feature. Each side is evaluated exactly the way `(is ...)`'s own right-hand side already is (`ComputeArithmetic`, recursively, over the same frozen `+`/`-`/`*`/`/` operators — `prolog-arith-unbound-variable`/`prolog-arith-not-numeric` fire identically for an unbound variable or a non-numeric leaf on either side), then compared numerically; `=:=`/`=\=` are numeric equality/inequality (`(is X Y)`-shaped values compared, never text), distinct from `=`/`\=` unification, which this item does not touch. `IsReservedPredicateName` (`VLA_Prolog.bas`) grows the six new names alongside `is`/`not`/`findall`/`!`, refusing them as user-defined predicate or table-column names by name, the same way `!` already is. `~days`. *Pays into:* `G-PROLOG`'s own sentence templates, which want "is greater than"/"is at least" phrasings the moment this exists to target.
  - ⬜ **PROLOG.8 — `=`/`\=` (unification/dis-unification) and `==`/`\==` (structural equality) as ordinary goals.** A real gap in `SolveGoalList`'s own dispatch (`VLA_Prolog.bas`, the flat `If predName = "is" Then` / `"not"` / `"findall"` chain `IsReservedPredicateName` already reserves four names for) — there is currently no way to unify two terms as a GOAL mid-body the way real Prolog's `(= X (f Y))` does, only implicitly, at argument-matching time against a stored fact or rule head. `\=` (succeeds exactly when its two arguments do NOT unify) is the routine complement, built the same way `SolveNegation` already wraps a bounded sub-call — `(\= X Y)` is definitionally `(not (= X Y))` and can literally be desugared to that rather than hand-rolled. `==`/`\==` are the STRICTER real-Prolog pair — structural identity with no binding at all, useful for comparing two already-ground terms (or confirming two variables are the SAME variable) without the side effect `=` has — a straightforward recursive structural walk, `VLA_Unify.UnifyTwoWay`'s own generic four-case shape with binding switched off. `IsReservedPredicateName` grows all four. `~days`–`~weeks`.
  - ⬜ **PROLOG.9 — type-checking goals (`var`/`nonvar`/`atom`/`number`/`atomic`/`compound`) and `between/3`.** None of the six ISO type-test predicates exist today (confirmed: no trace of `var`/`nonvar`/`atom`/`number`/`atomic`/`compound` anywhere in `VLA_Prolog.bas`'s dispatch or reserved-name list), and neither does `between(Low, High, X)`, real Prolog's ordinary bounded generate-and-test predicate (the direct complement to `findall`'s own harvest — "for each X between 1 and 10" has no expression today short of hand-authoring ten facts). Each type-test is a single, cheap runtime check against a resolved term's own shape (already-distinguished by `IsVarAtom`/`TermHasVariable`'s own existing classification, `VLA_Prolog.bas`) rather than new solving machinery — lower priority than `PROLOG.7`/`PROLOG.8` since nothing downstream currently needs a guard clause, but genuinely baseline, and cheap enough to build alongside them rather than as its own separate push. `~days`.
  - **Stated ceiling, carried forward from `BETA_ROADMAP1.md`, not built here:** first-argument clause indexing (`SQL`'s own hash-join law, `PROLOG`'s own twin — don't scan every clause per call); tabling/memoized resolution (SLG) — named specifically because it is what actually TERMINATES the textbook `ancestor(X,Y) :- ancestor(X,Z), parent(Z,Y)` recursive case rather than looping forever, the difference between a toy backtracker and something that survives a real KB, not a performance nicety; an `EXPLAIN` returning the proof tree (which facts/rules fired, in order), the same auditability reason `SQL`'s own `EXPLAIN` ceiling item already gives. **Explicitly not this engine's job, unchanged from `BETA_ROADMAP1.md`:** constraint/CSP solving — that instinct belongs to `SOLVE` (Answer Set Programming) below, a purpose-built generate-and-test notation, not a repurposed proof engine wearing an `in`/`all_different` costume.

- ✅ **`DATALOG(tables, rules)`** — the guaranteed-terminating third engine, built first per this section's own sequencing note (smallest proof of the shared-substrate bet — no compound-term unification, no backtracking, no cut — ahead of `SQL`'s full-relational tier or `PROLOG`'s ceiling). MVP, stratified negation, grouped aggregation, column-scoped table arguments, and comparison/arithmetic built-ins are all owner-tested live and committed: `src/VLA_Relation.bas` (substrate) + `src/VLA_Datalog.bas` (grammar, safety checks, engine, the `=DATALOG(...)` UDF), wired into both module manifests (`VLA_Build.bas`/`VLA_DevRig.bas`, F.15's own pair) and `src/VLA_Tests_Query.bas` (`TestDSLs` — pure for the MVP/negation/aggregation/builtins pins, `TestDatalogHostTable` needs a live workbook, see below). One stated limit remains by deliberate choice, not oversight (the recalc-caching item, its own bullet below). MVP scope, each piece a real sub-item:
  - ✅ **Function-free Horn clauses only.** The grammar refuses any rule containing a compound term as an argument (no `f(g(X))` nesting — variables and constants only), enforced at parse time (`datalog-compound-term`), not detected at runtime. That restriction is the entire termination proof. Program text is VLA's own S-expression syntax — `(fact (pred a b))`, `(rule (head V1 V2) (body1 ...) (body2 ...))`, `(query pred)` — reusing `VLA.VlaReadForms` rather than a second parser; a bare token starting A–Z is a variable, everything else a constant. Every rule's head variables must also appear in its body (the standard safety/range-restriction condition) — refused otherwise (`datalog-unsafe-head-variable`), and one predicate's arity is fixed everywhere it appears, across facts, rule heads/bodies, and table arguments alike (`datalog-arity-mismatch`).
  - ✅ **Facts sourced from a range or a `(fact ...)` block.** `VLA_Relation.RelFromRange` takes either a live Range or a plain 2D array (the seam that makes it testable with no workbook) — an Excel Table's header row is auto-stripped and its `ListObject.Name` becomes the predicate name (the "an `Employees` table IS a relation with no authoring step" case); a plain named range has no header, every row a fact, positionally. Renaming a table-derived predicate needs no new syntax — `(rule (reports_to X Y) (Employees X Y))` already expresses it with the one mechanism this engine has. **Pinned live, not just pure, and owner-confirmed:** `TestDatalogHostTable` (`VLA_Tests_Query.bas`) builds a real `ListObject` and a real Name-Manager alias pointing at the same cells, and calls `VLA_Datalog.DATALOG` directly — proving, on a live workbook, that a table reached through its alias is still queryable only by its own real `ListObject.Name`, and that a recursive rule sourced from a live Table's own `DataBodyRange` (not a hand-built array) derives correctly. Both are real bugs this MVP hit during development; neither could have been caught by a pure test alone. The owner additionally confirmed `not` against two real Tables (predicate names, not Name-Manager aliases) through an actual `=DATALOG(...)` cell formula, not just a direct VBA call.
  - ✅ **Semi-naive bottom-up fixpoint evaluation.** Round 1 evaluates every rule fully; every later round evaluates each rule once per body position, substituting the previous round's delta at that one position — the standard construction, correct for mutual recursion, terminating because function-free Horn clauses bound the whole universe of derivable tuples (a named `datalog-round-ceiling` safety valve at 10,000 rounds catches a pathological rule set rather than hanging). Reuses `VLA_Relation.RelJoin`'s hash join (index on the smaller side) via a small per-atom unification-lite layer (constant filtering, within-atom repeated-variable filtering) that `RelJoin` itself stays ignorant of.
  - ✅ **Results as a spilled array.** `VLA_Relation.RelToSpilledArray` — header row first, matching `SELECTROWS`'s own shape, this section's own frozen contract. Exactly one `(query pred)` per program names the result relation explicitly rather than guessing "the last rule's head," which would silently change meaning if rules were reordered.
  - **Stated limit, deliberately left as-is:** avoiding a full re-parse/re-fixpoint on every recalc (its own bullet below); a worksheet-function error surfaces as readable text in the cell (`"#DATALOG! ..."`) rather than Excel's own `#VALUE!`, since a UDF has no other visible surface for a refusal's words — first use of that pattern in this codebase, worth watching as a precedent for `SQL`/`PROLOG`/`SOLVE`.
  - ✅ **Stratified negation (`not`), DATALOG.1.** Owner-tested live and committed. Safe only because stratifiability — no predicate depending on itself through a `not`/`count`/`sum`, directly or through a cycle — is checked before the fixpoint runs, the same loud-and-specific discipline `datalog-unsafe-head-variable`/`datalog-arity-mismatch` already apply elsewhere in this engine, never detected live (`datalog-negation-not-stratifiable`). A rule body position can now be `(not (pred args...))` as well as a plain atom — every `not`'s own variables must already be bound by an earlier (written-order) positive body atom in the same rule (`datalog-negation-unsafe-variable`), since negation can never itself enumerate "every value not in this relation." `ComputeStrata` (`VLA_Datalog.bas`) builds the whole program's predicate dependency graph and solves each predicate's stratum via Bellman-Ford-shaped relaxation; `RunStratifiedFixpoint` replaces the MVP's single flat `RunFixpoint` (renamed `RunFixpointForRules`, unchanged internally), running each stratum's own rules to a full fixpoint, ascending, before the next stratum — a program using no `not` anywhere degenerates back to exactly the old single-call behavior. Built first of the two remaining sub-items specifically because it is what makes the stratification machinery exist at all — the earlier-simplifies-later move this whole tranche keeps making, one level down.
  - ✅ **Grouped aggregation (`count`/`sum` per group), DATALOG.2.** Owner-tested live and committed. The Datalog analogue of `SQL`'s own `GROUP BY` — deliberately sequenced *after* stratified negation, reusing its stratification rather than inventing a second one: an aggregate over predicate P is exactly as unsafe as a negated use of P if P is not fully computed first, so a `count`/`sum`-bearing rule sits in whatever stratum negation's own dependency graph would already assign it (`BodyItemNeedsFullRelation` is `True` for `not`/`count`/`sum` alike, sharing one code path through `ComputeStrata`, the semi-naive round loop, and `EvalRuleBody`'s own "read `relations()` in full" branch). Syntax: `(count Var (pred args...))` / `(sum Var (pred args...))` as a rule-body position — unlike `not`, the atom's own variables may be a *mix* of already-bound (the GROUP-BY key) and not-yet-bound (the thing counted, or — for `sum`, checked at parse time, exactly one such variable, `datalog-sum-needs-one-value-variable` — the value added up); `Var` is a brand-new result variable (refused if it collides with one already in scope, `datalog-aggregate-result-reused`). A group with no matching tuples at all is a real, meaningful zero — unlike `not`'s anti-join, an aggregate never drops a row.
  - ✅ **Column-scoped table arguments, DATALOG.3.** Owner-tested live and committed. Previously `TableArgName`/`RelFromRange` resolved `.ListObject` off *any* cell in the passed Range, so a partial-table selection (say, two columns of a five-column Table) silently expanded back to the *whole* table — the stated MVP limit. Fixed per the shape scoped here last time: the predicate name stays the parent Table's own `ListObject.Name` regardless of which columns were selected (`TableArgName`, `VLA_Datalog.bas`, unaffected by narrowing — it never reads `DataBodyRange` at all); only the *arity and values* narrow to the selected columns, positionally, the same "no column names, just position" philosophy the whole engine already uses (`SourceToArray`, `VLA_Relation.bas` — no longer always reads the *full* `DataBodyRange` once `.ListObject` resolves; a narrower, contiguous column span reads just that slice, still every data row — row-scoping was never part of this item's own stated limit and stays out of scope). A multi-area (Ctrl-selected, non-contiguous) column selection is refused by name (`datalog-table-noncontiguous-columns`, checked in `TableArgName` before `.ListObject` even gets a chance to resolve unpredictably against one) rather than silently guessed. `TestDatalogHostTable`'s own third scenario (`VLA_Tests_Query.bas`) proves both the narrowing and the refusal live — necessarily host-required, since a plain 2D array has no `.ListObject` to narrow at all. The owner additionally confirmed, live, four shapes the automated scenario doesn't reach: a column slice offset from the table's left edge (not just starting at column 1), narrowing all the way to a single column, Excel's own `Table[[Col]:[Col]]` structured-reference syntax resolving identically to a manual cell selection, and a zero-data-row table narrowed to fewer columns still reporting the right arity with no data rows.
  - ✅ **Comparison and arithmetic built-ins in rule bodies, DATALOG.4.** Owner-tested live (`TestDSLs` 89/89, plus five live `=DATALOG(...)` cell-formula checks including a comparison over a real Table column, a `(let ...)` arithmetic binding, and two refusal cases) and committed. The one standard-Datalog capability the engine still lacked: a rule-body position that filters or computes on *values* — real fact tables (salaries, dates, quantities) hit this fast. Two shapes, both reusing `ParseAtom`'s own atom-record shape directly (the operator symbol standing in as the "predicate," its operands as the "args") rather than inventing a second record: comparison filters (`(> X 50000)`, with the full set `<`/`<=`/`>`/`>=`/`=`/`<>`) and an arithmetic binding form (`(let Z (+ X Y))` — the four basic operators `+`/`-`/`*`/`/`, symmetric with comparison's own frozen six, a scoping call made this session since the roadmap's own `(let Z (+ X Y))` example never froze the operator set explicitly; exactly one brand-new result variable, refused otherwise via its own `datalog-let-result-reused`, the same one-new-variable discipline `datalog-sum-needs-one-value-variable` already enforces for `sum`). Safety is `not`'s own rule applied again: every operand variable must already be bound by an earlier (written-order) positive body atom (`datalog-builtin-unsafe-variable`), because a comparison can never itself enumerate "every value greater than 50000." Unlike `not`/`count`/`sum` these touch no stratification machinery at all — `BodyItemNeedsFullRelation` stays `False`, they evaluate inline in `EvalRuleBody` as per-row filters/computations. **Consumes SQL.1's own shared substrate rather than growing a twin, per this item's own sequencing note** — but not `EvalScalar`/`EvalBool` directly (SQL's own AST-walking shape doesn't fit DATALOG's flat two-operand atoms): the truly shared, DSL-ignorant part — a mechanical compare/compute given already-typed operands — is hoisted into `VLA_Relation.bas` (`ValueIsNumericType`/`IsInvariantNumericString`/`InvariantVal`/`CompareValues`/`ComputeArithmetic`), `VLA_Sql.bas`'s own former `CompareValues`/`IsNumericValue` now thin calls into it (`TableArgResolve`'s own SQL.1 precedent, repeated). What could *not* be shared as one policy: DATALOG's own rule-text constants and fact-block values are always plain VBA Strings, never a real Excel cell type (unlike a table-sourced value, or anything SQL's own `WHERE` ever compares), so a numeric-*looking* string counts as numeric for DATALOG (`IsInvariantNumericString`, locale-invariant) but deliberately not for SQL's own stricter, unchanged policy — each engine's own caller decides and passes the verdict in. Two real latent bugs caught and fixed while wiring this in, neither found by a naive first draft: `BodyItemNeedsFullRelation` returning `False` for a SECOND kind (the new `BI_CMP`/`BI_LET`, alongside `BI_POS`) broke the OLD assumption that "doesn't need the full relation" and "is a valid semi-naive delta position" were the same set — the round loop (`RunFixpointForRules`) now checks `BodyItemKind(...) = BI_POS` directly rather than the old `Not BodyItemNeedsFullRelation(...)`; and `ComputeStrata`'s own dependency-graph walk now skips a `BI_CMP`/`BI_LET` body item entirely rather than treating its own operator symbol (`"+"`, `">"`, ...) as if it were a real predicate name, which could otherwise collide with an actual predicate someone separately chose to name `+`. Tests: `VLA_Tests_Query.TestDatalogBuiltins`, pure (no live workbook needed, unlike DATALOG.3's own column-scoping) — a comparison over a table-sourced real-`Double` column, the same comparison over fact-block values chosen specifically (9 vs. 10 against a threshold of 8) to fail under a naive lexical-text fallback, a text-comparison fallback case, all four arithmetic operators, a RECURSIVE rule accumulating `(let ...)` across semi-naive rounds (path-length over a chain — the case that would have caught either of the two bugs above had they gone unfixed), a comparison composing with `(not ...)` in one rule body, and the full set of parse-time/eval-time refusals.
  - ✅ **Named-column atoms, DATALOG.5.** Owner-tested live (`TestDSLs` 118/118, plus two live `=DATALOG(...)` cell-formula checks: the item's own motivating example and an unknown-column refusal) and committed. Found by a phrasebook lookahead, not by engine work (2026-08-29): the first English sentence anyone would say about a salary table — *"Show every Staffing name whose salary is over 80000 as rich in cell E2"* — cannot be written against a purely positional engine, because the phrasebook row binds the word *salary* and has no way to turn it into "column 2" without reading the live header at translate time; the only sentence that reproduces `(Staffing X S)` literally is "...whose second column is over 80000," which nobody would ever say. So a body atom may *key* its arguments by header name — `(staffing (name X) (salary S))`, each argument a `(header Var-or-constant)` pair — resolved at call time against the parent Table's own header row, which `RelFromRange` already reads and strips (it now retains the names per table-derived predicate instead of discarding them, header names folded once through `VLA_Identity.Fold`, SD-8). Datalog stays positional *internally*: a keyed atom desugars to exactly the positional atom it stands for, every unmentioned column becoming a fresh anonymous variable, so arity is still the table's own (or, under DATALOG.3, the selected slice's — keyed names resolve within the slice only, since the slice is all the engine ever reads). Scope fences, all parse-time, all by name: keyed and positional arguments may not mix in one atom (`datalog-atom-mixed-keying`); a keyed atom against a predicate with no header — a `(fact ...)` block, a plain named range, or any rule-derived predicate — is refused (`datalog-keyed-atom-needs-header`); an unknown header name is refused *listing the names that exist* (`datalog-unknown-column`, the teaching-refusal shape); the same column keyed twice is refused; rule *heads* stay positional by definition (a derived predicate has no header to key against). **Consumes SQL.1's header-name map in `VLA_Relation.bas` rather than growing a twin** — the earlier-simplifies-later move one more time: the English front end is what forces DATALOG to borrow SQL's one piece of non-positional machinery, and it borrows rather than builds. Necessarily host-tested like DATALOG.3 (a plain 2D array has no header to key against), so the pure seam (`RelFromRange`'s array path) gains an optional has-header flag purely so `TestDSLs` can pin the desugaring without a workbook; `TestDatalogHostTable` gains the live scenario, including a mixed-case Table name and header (`Staffing`/`Salary`) proving both fold invariantly. *Pays into:* the first real English→DATALOG phrasebook row, and — since `PROLOG`/`SOLVE` source facts from the same Tables — the identical keyed-atom syntax for both, from the same substrate. `~days`.
  - ⬜ **DATALOG.6 — `min`/`max`/`avg` aggregation, alongside `count`/`sum`.** A real, concrete gap against `DATALOG`'s own sibling engine: `DATALOG.2` built exactly two aggregate forms, `BI_COUNT`/`BI_SUM` (private constants, `VLA_Datalog.bas`), while `SQL` next door already has all five as a generic, already-proven mechanism — `AGG_COUNT`/`AGG_SUM`/`AGG_MIN`/`AGG_MAX`/`AGG_AVG` (`VLA_Relation.bas`, the SHARED substrate both engines already build on) accumulate through one generic "running best/total so far" walker `ComputeGroupedRows`'s own `GROUP BY` already calls by kind. `DATALOG`'s own `(count N (pred ...))`/`(sum N (pred ...))` rule-body forms don't call that shared accumulator directly (their own grouping shape, over derived tuples rather than SQL's row-major `GROUP BY`, needed its own small walk), so this is real, scoped work — a `(min N (pred ...))`/`(max N (pred ...))`/`(avg N (pred ...))` triplet, each `BI_MIN`/`BI_MAX`/`BI_AVG` a new `BodyItemKind` sibling reusing `datalog-aggregate-bad-shape`/`datalog-aggregate-result-not-a-variable`/`datalog-aggregate-result-reused`'s own existing named refusals verbatim (they're already generic over "which aggregate form"), and `datalog-sum-needs-one-value-variable`'s own single-unbound-variable RULE applied to all three, though its own message text is `sum`-specific and would need a generalized sibling (or a `{form}`-templated rewrite) rather than a bare reuse. `~days`–`~weeks`.
  - ⬜ **Avoiding a full re-parse/re-fixpoint on every recalc — profiled first, not yet built.** `DATALOG()` re-parses `rulesText` and reruns `RunStratifiedFixpoint` from scratch every time Excel calls it. Worth naming precisely before touching it: Excel's own dependency-graph recalculation already skips calling `DATALOG()` at all unless one of its *own* argument cells changed (or a full/forced recalc, or Excel's dependency analysis gives up) — `DATALOG` declares no `Application.Volatile`, so the premise "it reruns on *every* recalc" overstates the common case. The real, narrower cost is: when it legitimately *does* need to rerun (one relevant cell changed), it redoes the *entire* fixpoint even if, say, only one fact-table row changed. A cache keyed on a hash of `rulesText` plus each table argument's own address would need a cheap "has this table's data actually changed" signal to be worth anything — Excel exposes no such checksum cheaply, so a naive cache would either re-read every table's full data anyway (undermining the savings) or accept staleness windows (an edited cell inside a table not triggering a re-derive) that this codebase's own "refuse loudly rather than silently wrong" culture would not accept quietly. **Conclusion: do not build a cache speculatively.** This needs a live, realistically-sized workbook to profile first (the owner's own domain — outside what this session can do without launching Excel COM automation, which needs the owner's own go-ahead every time). Revisit only once a real rule set or fact table is measured to make this matter.

- ⬜ **`SOLVE(facts, program)`** — Answer Set Programming, the fourth and last of this family, complementary rather than competing: the other three all answer some version of "what follows from what I know"; this one answers "what are all the self-consistent ways this could be, and which is best." Written like `DATALOG` (facts, rules) plus two new ingredients — **choice rules** (`{ assign(S,P) : eligible(P,S) } = 2 :- shift(S).`, "generate every possible way to pick 2 eligible people per shift") and **integrity constraints** (`:- assign(S,P), on_vacation(P,S).`, "discard any candidate world containing this") — so the program describes a whole space of candidate worlds and the solver hands back the ones that survive every constraint: an **answer set**. Not `ASP()` — a real, not hypothetical, collision with "average selling price" in finance spreadsheets, the same naming-collision discipline `BETA_ROADMAP1.md`'s own `GO.1` already applies elsewhere in this file. **The killer case, concretely:** staff scheduling, seating charts, resource allocation — "assign each person to a shift such that everyone works exactly 5 days, nobody works two in a row, every shift has at least 2 people, nobody's scheduled during their vacation days, total overtime is minimized." The thing people currently fight Excel's own Solver add-in over, except Solver is a numeric black box with no way to ask why this answer and not another, and `SOLVE` is built from the same named, inspectable facts as the other three (Sudoku/N-Queens are the honest hello-world, not the pitch). **`BETA_ROADMAP1.md`'s own MVP/Stretch/Ceiling breakdown predates the flat numbered shape `PROLOG`/`SQL` both settled on and is superseded by it below** — hydrated as `SOLVE.1`–`SOLVE.9` plus a stated ceiling, each item the smallest addition that turns the previous item's own output into the next item's own required input, "microscopes before dissections" the same discipline `SQL`'s own sequencing note names: no search machinery is built before there is exactly one candidate world to run it on; no world-scoring is built before there is more than one candidate world to choose between.
  - ⬜ **SOLVE.1 — the zero-choice base case: `DATALOG`'s own engine, unchanged, wearing the `SOLVE` name.** A `SOLVE` program with no choice rule and no integrity constraint is exactly a `DATALOG` program — one guaranteed, unique model, no search of any kind. Reuses `DatalogRun`/`RunStratifiedFixpoint` (`VLA_Datalog.bas`) wholesale: once `SOLVE`'s own parser has recognized a program's `(fact ...)`/`(rule ...)` forms as identical `DATALOG` syntax, `=SOLVE(...)` hands them straight to the same stratified fixpoint `DATALOG` already runs and reports its one derived relation set back as "the one answer set." Proves the framing — facts in, an answer set out, a `#SOLVE!`-style refusal (the same `fail:`/`Err.Description` convention `PROLOG`/`DATALOG`/`SQL` all already use) for malformed input — before either of `SOLVE`'s own two new ingredients exists to complicate it. `~days`.
  - ⬜ **SOLVE.2 — integrity constraints (`:- body.`) against that single candidate world.** Still zero search: with no choice rule yet, `SOLVE.1`'s own fixpoint produces exactly one candidate, so a constraint is a pure post-hoc CHECK — does `body` hold against the one derived model — never a reason to backtrack, since there is nothing else to try yet. The first point in this chain where "no answer set exists" is even a possible outcome, and — `BETA_ROADMAP1.md`'s own conclusion, carried forward — a first-class, auditable RESULT, not a crash: genuinely distinct from the `#SOLVE!` parse/shape-refusal path above, which stays reserved for malformed input, never for a world a constraint legitimately rejected. Reuses `DATALOG`'s own body-atom evaluator unchanged (the same walk a rule body already does) to check `body`. The smallest possible proof that a constraint is DIFFERENT from a rule — it derives nothing, it only eliminates — before search exists to make that distinction matter. `~days`.
  - ⬜ **SOLVE.3 — one choice rule (`{ p(X) : q(X) } = N`), naive enumerate-and-backtrack, no derived rules over the chosen atoms yet.** The first real search: `q(X)`'s own facts (already an ordinary `DATALOG`-style relation) name the candidate pool, and the solver enumerates every N-sized subset, checking each against `SOLVE.2`'s own constraints in turn, returning the first that survives (or `SOLVE.2`'s own "no answer set exists" result once every subset is exhausted). The try-a-candidate/recurse/backtrack-on-failure SHAPE is not new: it is `VLA_Prolog.bas`'s own `SolveGoalList` candidates loop, adapted from "try the next matching clause" to "try the next N-sized subset" — the same discipline, a different generator. Deliberately excludes a choice's own chosen atoms from ever appearing in another rule's body in this item (that composition is `SOLVE.4`), so a bug found here can only ever be in the enumeration or the constraint check, nothing else. `~weeks`.
  - ⬜ **SOLVE.4 — a choice rule's own chosen atoms feeding ordinary rules before constraints are checked.** The real scheduling shape: `assign(S,P)` gets chosen by `SOLVE.3`'s own search, an ordinary rule then derives `overtime(P)` from it via `SOLVE.1`'s own stratified fixpoint, and only THEN does `SOLVE.2`'s own constraint check run — against the FULLY DERIVED model, not the raw chosen set. Composes `SOLVE.1` and `SOLVE.3` rather than adding new machinery: each candidate subset `SOLVE.3` proposes is re-run through `RunStratifiedFixpoint` before being checked, exactly `DATALOG`'s own existing per-call cost, now paid once per candidate rather than once per query. `~days`–`~weeks`.
  - ⬜ **SOLVE.5 — more than one choice rule in the same program.** A real schedule has one choice per shift, not one choice total — this widens `SOLVE.3`'s own single-generator search into nested generators, one per choice rule, still fully naive (the Cartesian product of every choice's own candidate subsets, each full combination re-run through `SOLVE.4`'s own derive-then-check pipeline). A genuinely small increment over `SOLVE.3`/`SOLVE.4` — the enumeration primitive itself is unchanged, only how many of it run per program — but the first point where combinatorial cost becomes real, which is why performance (`SOLVE.9`, below) waits until there is an actual multi-choice program to profile against. `~days`.
  - ⬜ **SOLVE.6 — aggregates over a choice's own chosen set (`#count`, `#sum`) inside a constraint or a choice's own cardinality bound.** The killer case's own "every shift has at least 2 people" and "total overtime is minimized" both need to count or sum over the CURRENT CANDIDATE's chosen atoms, not over stored facts the way `DATALOG.2`/`DATALOG.6` (min/max/avg, itself still pending) aggregate — the same accumulation logic, reading from a different, per-candidate source. Reuses whichever of `DATALOG`'s own aggregate forms are built by the time this item is reached, generalized to read from a candidate set rather than a stored relation. `~weeks`.
  - ⬜ **SOLVE.7 — first-answer-set vs. all-answer-sets mode, spilled and `LIMIT`-capped.** Once `SOLVE.3`–`SOLVE.6`'s own search loop exists, returning either the first surviving candidate or every one up to a cap is a caller-facing mode switch over an already-complete search, not new search machinery — `DATALOG`'s own spilled-array return convention, reused rather than invented. Real motivation, not speculative: "how many valid schedules are there" and "show me a few options" are both ordinary asks the killer case's own stakeholders make once "does at least one exist" stops being the only question. `~days`.
  - ⬜ **SOLVE.8 — `#minimize`/`#maximize` (weak constraints): the best answer set, not just a valid one.** The single most business-valuable mode this engine has, named as such in this item's own original scoping — "the thing people currently fight Excel's own Solver add-in over." Runs `SOLVE.7`'s own all-answer-sets search to exhaustion (or an incremental bound-tightening variant of it, a real, owner-decidable choice left open here rather than assumed), scores each surviving candidate through an objective expression evaluated with `DATALOG`'s own arithmetic evaluator, and keeps the best. The one item in this chain whose cost can genuinely explode on a real workbook-sized problem — the reason `SOLVE.9`'s own pruning work exists, and the reason CDCL-style search stays at the ceiling rather than becoming a prerequisite. `~weeks`.
  - ⬜ **SOLVE.9 — search pruning (unit-propagation-style constraint short-circuiting) over `SOLVE.3`–`SOLVE.8`'s own naive backtracking, profiled first.** A performance item, not a semantics one — every answer this chain has already produced stays correct without it; what changes is how many dead-end candidates get generated before a constraint that was always going to fail them gets checked. `DATALOG`'s own recalc-caching item (above) sets the precedent this item follows: real profiling against a real scheduling-sized workbook before building anything, never speculative. Stops short of real conflict-driven (CDCL) search, which stays at the ceiling below. `~weeks`.
  - **Stated ceiling, carried forward from `BETA_ROADMAP1.md`, not built here:** real conflict-driven search (CDCL-style, not the propagation `SOLVE.9` already adds) to stay responsive at real problem sizes inside a live calc engine; disjunctive rule heads (`a | b :- body.`) for full theoretical ASP expressiveness, flagged as probably never needed for anything spreadsheet-shaped; classical/strong negation (`-a`, distinct from `not a`'s negation-as-failure, which `DATALOG`'s own stratification already covers) — no killer case named above needs it, and negation-as-failure alone already expresses every constraint this item's own scheduling example requires; an `EXPLAIN` showing which choices and constraints were binding, arguably more valuable here than for the other three, since "why is this the optimal schedule" is exactly what a human scheduler needs to trust this over Solver.
  - **Substrate relationship:** shares grounding and stratified derivation with `DATALOG` (`SOLVE.1`/`SOLVE.4`, the identical `RunStratifiedFixpoint`) and shares its own search/backtracking SHAPE with `PROLOG` (`SOLVE.3`, `SolveGoalList`'s own candidates-loop discipline, real combinatorial exploration rather than a fixpoint) — sitting at the genuine intersection of both rather than a separate fourth engine, exactly the shared-substrate bet the rest of this family already proved out.

# 🪴 TERRARIUM · DEFERRED, NON-CRITICAL BUGS

*A parking lot, not a department - owner-created after L0.2's own live regression turned up two real bugs neither one was looking for. The point of writing them down here instead of chasing them on the spot: finding a bug while doing something else is not itself a mandate to fix it right now, and without a place to put it, "just this one small fix" is exactly how a regression run for one item turns into three. Deliberately outside F.12's ID namespace - these are found, not planned, and triaging them properly (real repro, root cause, a fix) is itself real work, owed its own turn rather than squeezed in as a rider on whatever else was already in flight. Picked up after the roadmap above is closed out, not before; nothing here blocks anything above it.*

- ⬜ **TER-1 — `Check Instructions` appears to re-run a prior `Compile and Trace`.** Owner-found live, 2026-08-27, during L0.2's regression: `Compile and Trace` run successfully, then `Check Instructions` clicked right after - it visibly re-ran, as if it were another Compile/Trace, not a translate-only Check. A second `Check Instructions` click immediately after does NOT repeat this - only the first click after a run does. Root cause not yet investigated; a plausible lead, not a diagnosis: leftover armed trace/step-tracking state (`VLA_IDE.bas`'s `ArmTrace`) surviving from the Compile/Trace run into `DoCheck`'s own transpile probe - the same class of leftover-armed-state fragility the S5.3/S5.5/S5.6 history already documents once, for a different pair of callers.

- ⬜ **TER-2 — stale row-error marks survive a Check after the row's content is deleted.** Owner-found live, 2026-08-27, during L0.2's regression, root cause checked against the code, not just observed: `ClearMarks` (`VLA_IDE.bas`) only clears `B1:B<lastRow>`, and `lastRow` is `IdeLastRow(ws)` recomputed fresh on every call - if the row carrying the failing mark was the sheet's last non-empty row, deleting that row's content shrinks `lastRow` itself, so the clear range no longer reaches the very cell holding the stale mark it needs to erase. Fix direction, not yet built: `ClearMarks` needs to clear against the sheet's prior extent (or a safely-large fixed bound), not the freshly-recomputed one.

- ⬜ **TER-3 — audit `instructions.txt`/`VerifyReportChecks` coverage in both directions.** Owner-created 2026-08-27, prompted by this session's G-STRUCT pass: building real `VerifyReportChecks` assertions for G-STRUCT's own new `GStruct` sheet caught a genuine argument-order bug in `make {a} look like {b}` (copied the wrong direction) that a `test-success` proof could never have caught, and the SAME pass found the `Demo` sheet's entire "prelude vocabulary" block (styling, rows/columns, sort/filter/dedupe on a small table, sheet protect/unprotect) has run on every regression pass since it was written but has never once had a single `Report`/`CheckV` assertion - a wrong constant or reversed argument there currently shows up as nothing worse than "the script didn't crash." *(more: BETA_ROADMAP1.md)*
