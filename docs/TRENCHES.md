# TRENCHES.md — Campaign Histories From Below the Language Layer

*`LESSONS.md` remembers why the grammar's rules exist. This file is its sibling for the wars fought below that layer — first the interpreter's own build, and since, whatever else has demanded the same kind of ground-up, live-debugging campaign. `BETA_ROADMAP.md` states what shipped; this file remembers what it cost to learn it.*

# Part One — The Interpreter's Own Campaign History

*The interpreter, `VLA_Interpreter.bas`, built as a second, independent backend so the exported VBA would have something to be checked against instead of trusted on its own word. Written after the interpreter reached whole-corpus parity with the emitter — `instructions.txt` producing identical Output sheets under both backends, the goal `IN.3` named on day one and didn't reach for a very long time.*

## I. The dot count was the wrong denominator

`IN.2`'s own first estimate counted dot-forms in `english.vla` and got zero — a number that felt reassuring and measured the wrong thing entirely. The real cost wasn't the S-expression dot-forms (`font.bold`, `sort`, ...); it was the *receiverless* call heads `CallByName` can never reach at all, because `CallByName` dispatches on an object and half of VBA's own vocabulary (`MsgBox`, `WorksheetFunction.Sum`, a project's own standard-module helpers) has no object to dispatch on. Recounting properly found 37 of them, split cleanly into two shapes needing two different bridges — a small bare-builtin tier, hand-written one name at a time, and `Application.Run` against a module by name for everything living in `VLA_Runtime.bas`, needing exactly one mechanism instead of seventeen hand branches. The lesson that outlived this one measurement: **before pricing a piece of work, make sure the number you're counting is the number that actually costs something.** A metric that's easy to compute and wrong is worse than no metric — it buys false confidence at the price of a real one.

## II. `CallByName`'s silent lie

The first real Excel object this interpreter ever touched broke the plan on contact. `Application.Range`/`Cells`/`Rows`/... turned out to be *parameterized default members* — a documented late-binding blind spot, not a bug in this project's own heuristic — so `CallByName(Application, "range", ...)` simply failed, live, under both `Get` and `Method`, on `TestInterpreterObjectDispatch`'s maiden run. The fix was native dispatch: call `Range(...)` unqualified, the same thing the emitter's own generated code already does. That would have been the whole story, except the *next* host run found something worse: `Range.Value`, assigned through the same generic `CallByName` + `Let`-then-`Set` heuristic, didn't raise at all — it wrote a thirteen-digit garbage number into the cell instead of the value the program actually computed. No error, no signal, just a wrong answer sitting quietly where a right one belonged. `Value` turned out to be *also* a parameterized property under the hood, and `CallByName` doesn't know how to fail loudly when it can't cope with one. The fix — a native fast path, no `CallByName`, no reflection — closed this one instance. It would take the rest of the session to learn that this wasn't one instance of a rare edge case; it was the *first sighting of the actual shape of the problem*, and it would recur, silently, for as long as anything kept trusting `CallByName` with a member it had never actually been tried against.

## III. Parity that doesn't lie to itself

`IN.3`'s own opening line names its own limit before anyone else could: two backends agreeing proves *consistency*, not *truth* — a shared misunderstanding upstream reaches both identically and passes clean. The harness built to guard against exactly that reads every probe value back with a plain native `Range` read, never through either backend's own read path, so a bug shared by both backends' *readers* could never manufacture a false agreement with itself. It clears its own scratch sheet before every run, so a backend that raises before writing can never coast on the previous run's leftover value. And its very first real program caught a bug before any Excel run at all: the `for` loop's own probe program never declared its loop counter, which raw VLA's `Option Explicit` compile would have refused outright on the emitter side — an asymmetry invisible to the interpreter (a dynamically-typed dict has no such requirement) and exactly the kind of gap two independent implementations exist to surface. None of this made whole-corpus parity easy. It just meant that every step toward it, when it finally arrived, could be trusted rather than merely hoped for.

## IV. The trust question, answered by counting

Three separate live runs, in a row, broke `DynamicSet`'s `CallByName` `Let`/`Set` heuristic against three different real members — `value`, then `size`, then `color` — each with its own distinct failure shape (a silent garbage write, a loud type mismatch, an `Overflow`), and each patched exactly once its own crash was seen. After the third, the owner asked the question the pattern was already answering: *is patching the next crash still the right response, or should the heuristic simply stop being trusted?* The answer came from counting the whole corpus instead of arguing from three data points — every distinct `.`-set-position member `english.vla`'s own macros actually use, not the three that happened to crash first, turned out to be fifteen. All fifteen were converted to native dispatch in one pass, and the same audit found a second, unrelated bug hiding in plain sight: `application.screenupdating`-shaped bare dotted-global places were silently landing as fake plain-variable frame entries instead of ever touching the real object — no crash, because a wrong dictionary key doesn't raise, so nothing had ever said so. `"Turn off screen updating."`, ten sentences into `instructions.txt`, had never once actually turned off screen updating, the entire session, and nothing noticed until the trust question forced a real count instead of another single-crash patch. The `CallByName` fallback survives today only as a last resort for a member no real corpus use has ever reached — documented as genuinely unproven, not "probably fine," because by that point every member this project had ever actually tried through it had failed one way or another.

## V. Module scope, found by trying it

`IN.10`'s own scoping text left a question open on purpose: whether a call frame's isolation from module-level bindings would actually block whole-corpus parity, filed as "exactly the kind of thing to settle by reading the real corpus" rather than guessed either way. It was settled by trying it: `instructions.txt` defines a true top-level `const`, and a real called procedure reads it in its own body — a call frame built fresh and isolated raised "undefined variable" the first time anyone actually called it. The fix was narrow and read-only: a module frame, shared by construction with `main`'s own top-level execution, consulted only when a call frame's own lookup misses and never allowed to shadow a same-named parameter. The same read surfaced a second, unrelated gap while looking: `ExecStmt` had no case for `const` at all — grepped, not assumed, "const" had simply never appeared in the file before. Two fixes, one read, because reading the real thing the roadmap had deferred judgment on turned out cheaper than continuing to guess about it.

## VI. Buy the decision now

`IN.10`'s call/return mechanism was scoped in a single paragraph before a line of it was built, and the discipline paid for itself twice over once the scoping was actually checked against the live corpus instead of trusted on the strength of its own sketch. The original text filed named-argument binding as "this item's own remainder, once the frame exists" — as if it were separable, lower priority — and a real count of `instructions.txt`'s five called procedures found that filing wrong: three of the five need named binding, so a positional-only first cut would have reached two procedures out of five, not a usable slice of anything. The same measurement found a live bug the scoping pass's own reading surfaced rather than hid: the interpreter's top-level loop inlined the body of *every* top-level `(sub ...)` form unconditionally, not just `main` — a latent crash-or-garbage path that no existing test had ever triggered only because every program so far happened to declare exactly one procedure. And the return mechanism was checked against the real emitter, not assumed: `EmitReturn` turned out to also implement a self-recursive tail-call optimization, correctly judged out of scope for *correctness* (real recursion via a real call stack is correct without it) and explicitly not replicated — a found non-goal, named so it wouldn't quietly become a promise nobody meant to make.

## VII. The on-error build: sized honestly, then built in one pass

The interpreter's on-error/goto/label/resume remainder sat named and unpriced for most of the session — "`~weeks`, unpriced further, because the shape of the real remainder was not known" — until a pass dedicated to actually knowing it, rather than assuming it, found the real remainder was hours. Every real use in the corpus turned out to share one shape (`Try:`/`If that fails:`, always the same four forms in the same order), never crossing a call into a user procedure, which meant a single flat handler was enough — no stack, no call-frame-scoped state, because nothing in the real corpus needed either. The harder design question — telling a real, recoverable program error apart from the interpreter's own internal `Err.Raise` (its way of reporting bugs and gaps in itself) — resolved cleanly once someone actually checked: every one of this project's own hand-written raises carries a distinct `Err.Source`, verified by reading every `Err.Raise` in the file rather than assumed, so a real COM failure and an interpreter's own diagnostic could be told apart by source alone. The build's own first draft still shipped one real bug, caught by the owner's own test run rather than by the design review that preceded it: `err.description`, read inside a recovery block, came back empty. The cause was a piece of VBA behavior nobody had checked directly until it broke something — executing *any* `On Error` statement, not just an explicit clear, resets the real `Err` object's own properties, and the interpreter's own trapping mechanism was re-arming fresh for every statement while a handler stayed active, silently wiping the real failure before the recovery paragraph ever read it. The fix stopped trusting the live `Err` object to survive at all and shadowed it in the interpreter's own state instead — a smaller, more defensible design than the one that shipped first, found only because a test run refused to agree with a design that looked correct on paper.

## VIII. Whole-corpus parity, second act: the breadth pass and the census that missed twice

Once on-error stopped blocking whole-corpus parity, `VerifyReportInterpreter` ran clean past all three `Try:` blocks and straight into territory nobody had ever run the interpreter against: `instructions.txt`'s own "breadth pass" — thirty-odd styling, row/column, and sort/filter statements the file's own comment says exist to exercise already-shipped grammar "on its own merits." The first read of the failure concluded the whole statement-position dispatch tier was as unaudited as `DynamicSet` once was, and started writing code to fix all of it — until actually reading the neighboring function's body, not just its header comment, found eleven members already natively dispatched, no `CallByName` in sight. The real gap was narrower: two genuinely first-of-their-kind members reaching a parameterized default property for the first time, and a zero-argument method-call census that needed completing, not rebuilding. The census itself missed once on its own terms: a grep pattern that matched only macro bodies starting *directly* with a `.` call silently excluded any macro whose call sat inside its own `(begin ...)` wrapper, and `freeze-top-row`'s own `select` call was exactly that shape — found only on a second, owner-run reload that failed identically, forcing a second read done line by line instead of by pattern. And the tier's own two log-formatting helpers, `JoinKwArgs`/`JoinArgs`, carried a bug distinct from every dispatch fix around them: both called `CStr()` directly on a keyword argument's value for the sake of a readable log line, and `CStr` on an object invokes its default member — harmless for the single-cell ranges every prior keyword argument happened to be, and a bare, unwrapped "Type mismatch" the moment a real multi-cell range finally reached it, chased for seven straight live runs before `EffectLogTail` — logging the interpreter's own last few real actions into the failure message itself — finally said plainly where the run had actually died, rather than leaving it to be inferred from a bare error string a second and third time.

## IX. Twenty rounds, a wrong turn, and the question that cracked it

Whole-corpus parity's very last cell mismatch was the hardest bug of the whole build, and it earned that the honest way: by looking, at every stage, like something it wasn't. The first candidate was real and wrong at the same time — `CallByName`'s own "return value" for a void `Sub` target (`Collection.Add`) is genuinely undefined, and reading it via an expression can capture uninitialized memory, producing exactly the raw-pointer-shaped garbage the corpus was showing. Fixed cleanly, tested cleanly, and the bug came back unchanged on the very next live run. The second theory was built the same way and failed the same way: passing the array-holding argument list `ByRef` instead of `ByVal` through the dispatch chain, confirmed by a control test built specifically to isolate it — which also failed, live, identically. At that point the owner asked the question this whole file exists to remember: *this feels like another wild goose chase — is this digging in the right direction, or a deeper hole?* That question was correct, and it was the actual turning point, not because the prior fixes were foolish (both were real, defensible, and are still in the code for their own reasons) but because two "confirmed" fixes failing outright is a sign the *investigation method* needs to change, not the next patch. The method that changed: a standalone scratch module, dependent on nothing this project's own test harness provides, `Debug.Print` only, run with nothing else on the call stack and nothing else in the same test sweep — removing every possible confound the crowded, shared test file could never rule out. Eight scenarios later, the real mechanism stood alone: a scalar survives any number of nested procedure calls; an array survives zero hops; only an array-valued parameter, indexed *inline* as part of a `CallByName(...)` call's own argument list, after arriving through two or more levels of procedure-to-procedure forwarding, corrupts what `CallByName` actually receives — reproduced identically whether that parameter was declared `ByVal` or `ByRef`, finally settling that theory as a dead end rather than a partial answer. The fix, once the mechanism was known, was three lines: read each argument into an ordinary local variable before the `CallByName` call, never index the parameter inline at the call site. Both earlier "wrong" fixes were reverted or kept on their own remaining merits, not left in place pretending to have been the answer. The lesson isn't really about `CallByName`, arrays, or VBA parameter passing, though all three are real and now documented in the code. It's that **when a fix keeps being confirmed and then failing live, the fastest way forward is not a better theory — it's a smaller, more isolated test than the one that produced the wrong theory in the first place**, and a collaborator willing to say "this feels like a wild goose chase" out loud, before the tenth theory instead of after it, is not friction. It's the thing that ends the chase.

# Part Two — The Column-Deletion War

*Not an interpreter bug — both backends produced identical, correct VBA; the fault was somewhere Excel itself decides what a delete does. Filed here anyway, in the same voice and for the same reason: this was a ground-up, live-debugging campaign in exactly the interpreter's own tradition, and `docs/BETA_ROADMAP.md`'s TER-4 has the roadmap-side record. This part has one entry, because the war isn't over — see its own closing line.*

## X. The bug that outlasted every theory

G-STRUCT's own `VerifyReportChecks` came back with a failure list that looked, on its face, like eight independent rule bugs — `move-column`, `copy-formats`, `copy-style`, `copy-formulas`, `paste-transposed`, `cut-range`, `delete-shift-left`, a stray `fill-series` default — scattered across both backends, and worse, the list *changed shape* between reports that should have been identical, rules failing in one report and passing in the next with nothing in the code between them. Every one of the failing rules, extracted verbatim from the real compiled module into a standalone `Sub` and run directly, passed cleanly, every time, no exceptions — the actual VBA being generated was correct. That gap — real code, correct in isolation, wrong in the real run — is what made this the longest live bug the project has chased, because it meant the rules were never the thing to keep investigating, and nearly every hour of the session went into investigating them anyway before that was understood.

The first real break looked like the whole answer and wasn't: `VerifyReport()` had never once triggered its own Compile-and-Trace — it just read whatever was already sitting on the `Output` sheet, on the documented-but-unenforced assumption that the caller had run one moments before. A session spent alternating between Compile-and-Trace and Interpret-and-Trace, chasing an unrelated bug, violated that assumption constantly, and every violation produced a fully-formed, plausible, *wrong* report — a real cell address, a real "not bold," labeled "emitter" while actually reading the interpreter's leftover cells. A durable provenance marker, stamped by every real run and checked before any report trusted a cell, closed that hole for good — and changed nothing about the failure list. The rules were still failing, honestly, under a harness now honestly reading the right sheet.

What followed was a small museum of disproven theories, each one reasoned carefully, each one tested directly rather than argued from a desk, each one wrong: the emitter's own `Call obj.Method(Keyword:=Value)` syntax, tested by hand in the Immediate window against the exact generated shape — clean. `Application.ScreenUpdating`, on and off, across the full sequence — no difference. Frozen panes on the affected sheet — irrelevant; a manual check on a fresh row of the same sheet came back perfect. `Application.Run` versus direct execution — identical. The whole populated workbook's own accumulated state, tested by running the standalone repro immediately after a real completed run — still clean. A standing `On Error GoTo` handler, matching the real compiled module's own error-trapping structure exactly — no change. Ten separate, well-reasoned differences between "the isolated repro" and "the real run," and ten times the machine said no.

The bug finally gave ground not to a theory but to instrumentation planted directly in the live, real, compiled code — no repro, no transcription, a `Debug.Print` inserted after the real `PasteSpecial` call in the real generated module, run by hand from the VBE. It printed `True`. A second probe, at the very last line of the real `main`, printed `False`. The operation had genuinely succeeded; something later in the same run had genuinely undone it. Bisecting `instructions.txt` itself down to a single truncated file isolated the culprit to one statement, `trim-sheet`; bisecting that one Sub's own two delete loops — Find alone, both loops, each loop alone — isolated it further, to `EntireColumn.Delete` specifically, reliably, every time, with the sibling `EntireRow.Delete` loop innocent throughout. A bounded delete margin, an explicit `CutCopyMode` clear, and row-by-row deletion in place of one bulk call were each proposed as the fix — the second on the owner's own diagnostic instinct, tried instead of one more round of theorizing — and each, tested live, changed nothing. The one variable left standing pointed at `move-column`'s own earlier column Cut+Insert having already run in the same execution; reordering it to run after `trim-sheet` instead of before was the obvious next fix, confirmed by every isolation step that preceded it — and it also failed, live, on the first test, disproving the ordering theory the entire isolation campaign had been pointing toward.

It is parked in `docs/BETA_ROADMAP.md`'s TER-4, unresolved, on the owner's own words at the end of a very long night: a fine parking spot for now, but "essentially giving up and kicking the can down the road," said plainly rather than dressed up as a resolution — and the record was corrected the same night rather than left standing on the disproven theory, because a war story that quietly keeps its false ending is worse than one that admits it doesn't have one yet. What survives this entry isn't a fix. It's a map of exactly which floors have been checked - every one of them solid - and an honest floor plan of the one that hasn't: whether `move-column` running anywhere in the same execution is a real precondition for the bug, or was never the actual factor at all, was never actually isolated before the session ended. The next session inherits that one clean, still-open question, not a pile of ash where ten confident theories used to stand.

## XI. The column was never reverted — it was deleted

The next session picked up the one clean question entry X left behind and answered it the honest way: not by theorizing further, but by bisecting for real. Five throwaway scripts, each `gstruct.txt` with exactly one earlier structural operation removed — hide/unhide, group/ungroup, row insert/delete, `move-column`, freeze-panes — plus a same-session control run unmodified first. All six reverted C60/C62 exactly as before. That single round of live tests did something no amount of desk-reasoning had: it closed the door entry X left open. `move-column` was never the precondition. Neither was any of the other four, alone. Whatever this bug actually was, it wasn't about which sentence ran before `trim-sheet` — every candidate got individually cleared.

The next test asked the opposite question — keep only one candidate instead of removing one — and looked, for one report, like it had cracked the case: a sixth variant with all five omitted at once came back clean, suggesting the five were independently sufficient rather than jointly necessary. Round two, testing each candidate alone, came back a mess that took real discipline to read honestly instead of just recording: three variants (hide, group, freeze) came back clean, but for a reason that had nothing to do with the bug — with no real values anywhere on those sheets, `VlaTrimSheet`'s own content-only `Find` found nothing at all and exited before its delete loop ever ran. The other two (insert-delete, move-column) came back with a failure that had never appeared before in this entire investigation: A60 itself, blank — the one cell that had been immune for the whole of entry X, because it was never touched by PasteSpecial at all. That wasn't the bug being chased. It was a second, different bug, hiding inside the test rig built to catch the first one, and it had to be recognized as different before it could be set aside instead of chased down the wrong hallway.

That second bug turned out to be real and fixable on its own terms: `Find(What:="*")` matches cell *content*, not formatting, so a row holding nothing but bold text with no value was invisible to it — `VlaTrimSheet` mistook a genuinely-formatted row for trailing-empty and deleted it whole. Fixed properly: bounds computed as the max across content Find *and* format-only Find, in both row order and column order, not one Find doing double duty for two different questions. It shipped as a fix for its own sake, a real correctness bug independent of TER-4 — and then, almost as an afterthought, `bisect_f_baseline.txt` got run again against it, unmodified, no anchor, the exact scenario that had reverted C60/C62 for two sessions running.

It came back clean. A60, C60, C62, all correctly bold and red. The side quest was the main quest. It had been the whole time.

The mechanism, once visible, explained everything entry X had catalogued as mysterious and left unexplained: the old code used one row-order `Find` for *both* bounds. `fill-series` wrote real values down to row 203, but only in column A; other real content — the transposed copy, the shifted row-90 data — sat in columns out to E, at shallower rows. Row-order search cares about row number first, so it locked onto `A203` and reported the sheet's rightmost column as column A. The delete loop then ran, correctly, exactly as written, from column 2 outward for its entire span — deleting essentially every column from B through 200, including column C, where C60 and C62 lived. Column A was never touched, because it *was* the boundary. Nothing had reverted. Column C had been deleted outright, and blank content from far to the right shifted in behind it. Every floor entry X had marked solid was solid for the same reason: none of them changed the column layout that produced the wrong boundary. The eight rules that failed together weren't eight bugs. They were eight rules that happened to write into columns B through E.

Two smaller bugs still stood between this and a clean report, and both were worth their own honest accounting rather than a quiet fix. The first was a stale assumption in the test script itself — `Clear range` only clears content, and `VlaTrimSheet`, now correctly protecting live formatting, was right to refuse deleting a cell that was still genuinely bold. The test needed `Clear everything from`, not the code. The second took two passes: `cut-range` failing only in the interpreter looked, at first, like the exact bug this file's own entry IX already diagnosed once — an object silently coerced through its default member instead of assigned by reference — and the fix for that theory was correct, confirmed, and changed nothing, because it wasn't the whole bug. A diagnostic line planted directly at the point of failure, not another round of reading the code and theorizing about it, showed the object reference was intact all along; the real fault was one line further down, `IsEmpty()` called on an object argument, silently deferring to its default member instead of testing whether a reference was present. Two real, distinct bugs, stacked on three lines, and the second one only gave itself up to instrumentation, the same way the original mystery in entry X did. This project keeps re-learning that lesson because it keeps being true.

TER-4 closes here, across two sessions and something north of six hours of live testing on the second one alone. It closes on a note worth keeping: the fix that mattered most didn't come from staring harder at the bug everyone was staring at. It came from fixing an adjacent, smaller, fully-understood bug for its own sake, and only afterward discovering it had been the answer to the larger question the whole time. Bisect for the truth, not for the theory you're already attached to — and when a side quest turns up a real, honestly-explainable bug, fix it and go check whether it was ever a side quest at all.
