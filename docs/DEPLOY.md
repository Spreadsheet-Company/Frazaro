# Deploying Frazaro

## Which download should I use?

Two ways to get Frazaro, and the honest answer is "start with the standalone add-in unless you already know your machine allows installers." This section is written to be reusable near-verbatim as the self-identifying copy beside a future website's or repo's download links — the two paths are a permanent doctrine, not a temporary state.

**Before either download — the open security items.** Three findings from the project's own threat model are open in this beta (`SEC.1` dispatch gating, `SEC.2` `raw` consent, `SEC.3` provenance); `README.md`'s *Known open security items* section states each in plain words and what it means for you. The one line that matters until they close: load phrasebooks only from people you would accept a macro-enabled workbook from. The downloads' embedded phrasebooks are audited at build time; a `.vla` someone sends you is not. Frazaro does not update itself, so check that section when you come back for a newer build.

| | **Standalone add-in** (`Frazaro_English.xlam`, or `Frazaro_Espanol.xlam` for the Spanish edition — `EDITION-MANIFEST`) | **Installer** (`FrazaroSetup.exe`, English edition only today) |
|---|---|---|
| **Choose this if** | You're not sure, or you're on a work computer managed by IT. It's an Office document, not a program — it works everywhere Excel does. | This is your own machine and you want a one-click setup with a normal Windows uninstall entry. |
| **Avoid if** | — (this is the universal default) | Your IT department blocks running downloaded `.exe` files. If the installer won't run, the standalone add-in always will — use that instead. |
| **What it needs, once** | If this release's VBA project was signed (see "Code signing" below — a manual, per-release maintainer step; the one-click trust-and-remember behavior is owner-verified, not just documented): trust the publisher when Excel first asks, one click, ever. Either way, register it with Excel — a one-click **"Register for auto-load"** ribbon button (owner-verified) does this from inside the product itself; the Add-ins dialog checkbox works too, if preferred. | Nothing beyond running the installer — registration is automatic. |
| **Files involved today** | One: `VlaBuildAddin` embeds `prelude.vla`/`english.vla` inside `Frazaro.xlam` itself (very-hidden sheets, read back only when no external file is found — an external copy still overrides, unchanged). Owner-verified, not just written — see the note below the table. | One: `FrazaroSetup.exe` (it contains all three). |
| **Removing it** | The in-ribbon **"Uninstall Frazaro"** button: deregisters, then genuinely deletes the file itself (a retrying background process, not a fixed delay and not a "delete this by hand" message) or hands off to the real uninstaller if this copy was exe-installed. A real click-through already caught and fixed one structural bug in the timing — see "Updating or removing" below for the full sequence before trusting this row. | The same button works here too, *or* the normal Windows Settings → Apps uninstall entry. |

Both paths now get an identical one-click exit inside the product itself (pending live verification of the standalone case's genuine self-delete — see "Removing it" above), regardless of which one a person used to get in. The reason to lead with the standalone add-in isn't this symmetry, though — it's the row that never changes: it's the one path with no `.exe`-execution policy to trip over, which is the actual failure mode on a managed machine.

**Bundling's real status: owner-verified, all three failure combinations.** `TestEmbeddedTextFallback` (host test) proves the reader round-trips written sheet content in isolation. Live, end to end: renamed `prelude.vla` away and ran a fresh workbook's Interpret + Compile clean (prelude-fallback alone); with `prelude.vla` still renamed, also renamed `english.vla` away and retested clean (both fallbacks active simultaneously); renamed `prelude.vla` back and retested clean once more (vocab-fallback alone, external prelude restored and confirmed still taking priority). No errors in any of the three states.

## Building the add-in (developer, once per release)

1. In the development workbook (all modules imported and working), import `VLA_Build.bas`.
2. **Debug → Compile VBAProject** — and fix anything it finds. VBA compiles lazily, so uncompiled code can hide undefined references indefinitely; this step is what keeps them out of the shipped add-in.
3. Immediate window: `VlaBuildAddin`. **EDITION-MANIFEST:** a bare call now builds every known edition in one pass — `Frazaro_English.xlam` and `Frazaro_Espanol.xlam` today (`VlaEditionNames`, `VLA_Build.bas`) — the same "run everything, report everything, one failure doesn't hide the rest" shape `VlaSelfTest` already uses for tests; one edition's bad phrasebook doesn't stop the others from building. Pass an edition name, `VlaBuildAddin "Espanol"`, to build just that one instead (a dev-iteration convenience). For each edition, the build **audits its own phrasebook chain** — `english.vla` alone for the English edition, `english.vla` then `scripts\polyglotta\espanol.vla` layered on top for Spanish (every non-English edition is bilingual by construction today: its overlay file is thin and depends on `english.vla`'s own macros, so `english.vla` always loads first) — loading it fresh runs every `test-success`/`test-fail` form, then duplicate signatures and lint hazards are checked; any defect refuses that edition's build (the others still build) with the report. It then exports the current engine modules — `VLA_Identity`, `VLA_HeadTable`, `VLA`, `VlaFrame`, `VLA_Loader`, `VLA_English`, `VLA_SentenceEngine`, `VLA_Runtime`, `VLA_Interpreter`, `VLA_Events`, `VLA_EventSink`, `VLA_IDE` — the SAME module list for every edition — assembles them into a fresh project named `VlaTools`, adds the open/close handlers that manage the **Frazaro** menu and register the event sink (IN.7), injects a **Frazaro ribbon tab** (a `customUI14` part, via a generated PowerShell step, run automatically and synchronously — if PowerShell is unavailable the build still succeeds, prints the script path to run by hand, and the legacy Add-ins menu carries all the same commands, still English for every edition today — `EDITION-CHROME`'s own job), and saves the edition's own named `.xlam` next to the workbook.
4. **Manual step one, per `.xlam` built** (it was "the one manual step" until signing joined the release sequence on 2026-09-08 — there are two now): open it, press Alt+F11, right-click `VlaTools` → *VlaTools Properties* → *Protection* → check *Lock project for viewing*, set a password, save. (VBA offers no API for this.) Locking is part of the error story: it makes the VBE's Debug button a dead end for users even in edge cases.
5. **Manual step two, per `.xlam` built**: sign the VBA project — Alt+F11 → Tools → Digital Signature… → Choose Certificate… → save. Full detail, including minting the certificate once per machine, is under "Signing the VBA project" below. This is what earns the downloader a one-click **"Trust all from publisher"** instead of a bare Enable/Disable Macros modal, and `release.ps1` will refuse without `-Signed`.
6. Distribute one file per edition: each `.xlam` embeds its own phrasebook chain and `prelude.vla` as very-hidden sheets (same mechanism `VLA_Runtime`'s injectable text already uses), read back whenever no external file is found beside the add-in or the user's own workbook, owner-verified live for the English edition (see "Which download should I use?" above). The three-file distribution and the Inno Setup installer both still work identically for the English edition — bundling only removed the requirement, not the option; the installer itself is still English-only today (`EDITION-ESPANOL`'s own first per-edition distribution pass).
7. **DI.3a:** `VlaBuildAddin` also writes `installer\version.iss` (`#define MyAppVersion "<VLA.VLA_RELEASE_VERSION>"`), once per call regardless of how many editions it built — the installer's own build step below `#include`s it instead of carrying a hand-typed literal. Run this step at least once before building the installer, or `Frazaro.iss` will fail to find `version.iss`.

The `.bas`/`.cls` files remain the source of truth in version control; the `.xlam` is a build artifact. Rebuild by re-running `VlaBuildAddin` after any module change.

**Dev convenience — a `Frazaro_Beta.xlam` test copy stays current on its own, including being created.** `VlaBuildAddin` creates and refreshes a `Frazaro_Beta.xlam` copy beside the dev workbook on every build, unconditionally — register it once for auto-load (the ribbon button, see above) and forget it exists. First shipped opt-in (only refresh a copy that already existed, so "a fresh checkout never sees it appear on its own"); corrected immediately after it met the Uninstall Frazaro button in practice — Uninstall's own successful self-delete removes this file entirely, and the opt-in gate then meant the convenience died silently and permanently the moment that happened, recoverable only by manually redoing the exact copy/rename step it exists to eliminate. Since this module never ships (it's not in `VlaBuildAddin`'s own module list), the cost of "an extra file might surprise someone" was never as high as "this silently stops working the first time its two features are actually used together." It closes the copy first if this same Excel session has it open, not because the file would otherwise be locked (a bare file copy succeeds over an open `.xlam` regardless — live-tested; Office uses its own advisory `~$` lock-file convention, not an exclusive OS handle) but because overwriting the bytes under an already-loaded session doesn't retroactively update that session's own in-memory code. If that copy happens to be open in a *different* Excel process, this can't reach it at all and says so in the build report.

## Releasing (daily patch, weekly minor)

The working loop is **Scope → Implement → Test → Build → Push**, and since the `0.5.0` public import (2026-09-05) the last step is a release, not just a push. Cadence, an owner decision of 2026-09-07 that fixes SD-14's tempo without changing its numbering: a **`0.5.N` patch release at the end of each working day** and a **`0.N.0` minor release at the end of each week**, with security and safety fixes front-loaded into the patches and larger feature additions landing in the minors. The `.xlam` editions are release assets, never tracked files; `README.md`'s download links resolve to whatever release is newest.

`tools\release.ps1` is the Push step, one command:

```powershell
powershell -File tools\release.ps1 -Version 0.5.1 -Locked          # add -DryRun to rehearse
```

It refuses to touch the remote unless all of the following hold, and says which one failed: on `main`, clean, not behind origin; `VLA_RELEASE_VERSION` in `VLA.bas` equals the version asked for (bumped by hand, at release, per DI.3a); the tag is not taken; `docs/RELEASES.md` has a `## <version>` section (notes are written *before* the release); every `tools\check_*.ps1` exits 0; both edition `.xlam` files exist beside the repository root and are newer than every file under `src/` and `scripts/` (the build ran after the last edit); and `-Locked` was passed, the owner's attestation that step 4 above was done for both editions, since VBA offers no API to check it. Then it pushes `main`, tags `v<version>`, pushes the tag, and publishes the GitHub release with the two `.xlam` assets and the notes section. Release tags are immutable on GitHub (a ruleset forbids deleting or moving `v*`), so a wrong release is fixed by the next patch number, never by rewriting. The same `check_*.ps1` scripts run in CI on every push and pull request (`.github/workflows/checks.yml`).

Day-end sequence, then: bump `VLA_RELEASE_VERSION`, reload, self-tests and goldens, `VlaBuildAddin`, **lock both projects, sign both projects**, write the `## <version>` section, run the script.

**Signing joined the standard sequence on 2026-09-08 (owner decision), having previously been a separate, optional section.** The reason is that it is the only step that changes what a *downloader* sees: an unsigned `.xlam` gives them a bare Enable/Disable Macros modal with no trust option, while a signed one offers **"Trust all from publisher"**, after which every future launch is silent. Leaving it outside the sequence meant the friction this project spends real effort removing was being reintroduced at the last step of every release. Like locking, VBA exposes no API for it, so `release.ps1` takes `-Signed` as an attestation exactly the way it already takes `-Locked` — two separate switches, not one combined flag, so attesting to one cannot silently attest to the other.

## Code signing (DI.1)

Two genuinely separate signatures, on two different artifacts, answering two different trust questions — kept apart deliberately rather than glossed as one "signing" step.

### Signing the installer executable

**The `.xlam` itself cannot be Authenticode-signed** — tried directly in `VLA_Build.bas` and found not to work, empirically: `Set-AuthenticodeSignature` on a real `.xlam` fails with *"The form specified for the subject is not one supported or known by the specified trust provider."* This is structural, not a missing-cert or missing-tool problem — Office's OOXML package format (which `.xlam`/`.xlsm`/`.docm` all are) has no registered Authenticode Subject Interface Package on Windows. Confirmed by the same mechanism signing a plain `.ps1` file cleanly on the same machine, so the mechanism itself is not the problem.

Signing instead targets the **installer executable** (`installer/sign_installer.ps1`, run after `ISCC.exe` builds `FrazaroSetup.exe`) — a `.exe` is a standard, fully-supported Authenticode target. It uses a **self-signed** certificate (`New-SelfSignedCertificate` / `Set-AuthenticodeSignature`, both built into Windows PowerShell — no separate signtool/Windows-SDK install needed), generated once per dev machine (`Cert:\CurrentUser\My`, subject `CN=Frazaro Dev Signing`, reused on later runs by subject match rather than re-minted every time).

**What this buys, and what it does not.** A signed installer gives it a stable "this came from the same publisher across releases" identity and removes one class of tampering-in-transit risk on the one artifact that's actually signable this way. It does **not** touch Excel's own macro-trust story at all — the `.xlam` inside is unsigned regardless. And a self-signed certificate has no chain to a root CA, so even the installer itself is not automatically trusted by Windows SmartScreen — a user (or their IT department) would still need to explicitly trust the certificate. That is real work someone has to do, once, and this script does not do it for them.

### Signing the VBA project — a different mechanism entirely

Office documents carry their own signature mechanism, separate from Authenticode: the VBE's *Tools → Digital Signature* dialog signs the **VBA project itself**, governed by Excel's macro-security model rather than the Trust Center's VBOM setting. This is the one lever that actually reduces friction on the add-in a user opens: the first time someone opens a workbook whose macros are signed, Excel offers **"Trust all from publisher"** — click once, and every future launch is silent, no warning at all. This works with a **self-signed certificate** — unlike SmartScreen's exe reputation, the one-click "trust this publisher, remember it" flow doesn't require a CA chain.

**Live-verified, not just documented.** Presented as a modal dialog with a dedicated button on this Excel build, not the inline ribbon-style "Enable Content" bar assumed from documentation before this was tested — the underlying mechanism is what mattered, not the exact widget. Owner-verified all three states in sequence: unsigned shows a plain "Microsoft Excel Security Notice" modal with no trust option, just Enable/Disable Macros; signed but not-yet-trusted shows the same modal reading *"The digital signature is valid, but the signature is from a publisher whom you have not yet chosen to trust,"* now with a third button, **"Trust all from publisher"**; after clicking it, closing Excel, and reopening a third time, no dialog at all — trust genuinely persists rather than resetting per session.

`tools/generate_vba_signing_cert.ps1` mints (or reuses) the certificate — subject `CN=Frazaro VBA Signing`, deliberately a **separate certificate** from the installer's `CN=Frazaro Dev Signing`, since the two sign different things under different trust models and sharing one would blur which trust conversation a given signature answers. What it cannot do: select that certificate in the VBE and actually sign the project. Confirmed directly, not assumed — `VBProject`'s live COM interface was enumerated via Excel automation and carries no signing-related member at all (`Application`, `BuildFileName`, `Collection`, `Description`, `FileName`, `HelpContextID`, `HelpFile`, `MakeCompiledFile`, `Mode`, `Name`, `Parent`, `Protection`, `References`, `SaveAs`, `Saved`, `Type`, `VBE`) — the identical "VBA offers no API for this" limitation `VLA_Build.bas` already documents for project locking. **This step is manual, every release:**

1. Run `tools/generate_vba_signing_cert.ps1` (prints the certificate's subject and thumbprint; safe to re-run — it reuses an existing certificate rather than minting a new one each time).
2. Open a built `.xlam` in the VBE (Alt+F11). **Once per edition** — `Frazaro_English.xlam` *and* `Frazaro_Espanol.xlam` today, the same per-file manual loop locking already needs. (This step read "the built `Frazaro.xlam`" until 2026-09-08, singular, written before `EDITION-MANIFEST` made the build produce two editions; following it literally signed English and shipped Spanish unsigned.)
3. Tools → Digital Signature… → Choose Certificate… → select the one printed above → OK.
4. Save the workbook.

Do this **after** locking and **before** running `tools\release.ps1`, which now
requires `-Signed` alongside `-Locked` — see "Releasing" below. Signing after a
release is published is too late: the assets are already uploaded, and `v*` tags
are immutable, so an unsigned asset is corrected by the next patch number rather
than by replacing the file.

**How, methodologically:** no COM surface exists to drive the VBE's signing dialog from outside, so this needed a human click-through — and a second machine or fresh Windows profile turned out not to be necessary either. The real blocker on a dev machine is its macro-security level (`VBAWarnings`) usually being set to "Enable all macros," which suppresses any trust prompt regardless of signing — confirmed directly on this machine (`VBAWarnings=1`), not assumed. `tools/toggle_vba_warning_level.ps1` flips it to "Disable with notification" (saving the prior value first) so the real prompt shows on the same machine, and `-Restore` flips it back afterward — remember to run that once the manual check above is done.

### Protected View / Mark-of-the-Web — a separate gate, neither signature above reaches

A directly-distributed `.xlam` opened on a fresh machine can hit *"This file type is not supported in Protected View"* — a hard refusal, not the usual "Enable Editing" banner, because Add-ins are one of the file types Protected View's sandbox can't open at all (it would have to execute code at load). This is gated on the file's **provenance** (does it carry a Mark-of-the-Web / `Zone.Identifier` tag from however it arrived — browser download, email attachment, zip extraction, some network/cloud paths), which is checked before and independently of any code-signing trust decision. Neither signature above touches it: the `.xlam` can't be Authenticode-signed at all (previous subsection), and VBA-project signing governs the macro-trust prompt, a different conversation entirely. See "Standalone" below for the real mechanism and fix — a Trusted Location works but is the heaviest option; unblocking the one file is usually enough.

**Why self-signed and not a purchased certificate, for now, for both signatures above:** IN.9 already removed the harder half of the trust conversation — the default runtime (Interpret) touches no VBProject and needs no Trust Center change at all; only Compile (the export path) does. A purchased code-signing certificate becomes worth its cost once real distribution to machines outside this project's control is happening; buying one on spec, before that, is exactly the kind of decision this project's own roadmap (SD-10, and the cost-of-delay discipline in `METAMETALISP4.md`) says to defer until the option is actually expiring. Revisit once a pilot's IT policy (`PI.7`) is known.

## Installing (each user, once)

See "Which download should I use?" above for which of these two paths to lead with — it depends on the machine, not on which is more polished.

### The Inno Setup installer — for an unmanaged, personal machine

`installer/Frazaro.iss` builds a per-user installer (`FrazaroSetup.exe`) with `ISCC.exe` (Inno Setup 6). It:

- Installs `Frazaro.xlam` and `scripts\prelude.vla` / `scripts\english.vla` under `%AppData%\Frazaro` — no administrator rights required, and this exact `scripts\` layout is what `VLA.PreludeVlaPath` and `VLA_IDE.IdeVocabPath` already look for beside the add-in.
- **Registers the add-in with Excel automatically** — writes `Frazaro.xlam`'s path into the next free `OPEN`/`OPENn` slot under `HKCU\Software\Microsoft\Office\<version>\Excel\Options` (looped over every installed Office version that has an `Excel\Options` key), the same registry entry the Add-Ins dialog itself writes when you tick a box — so there's no separate "Browse to Frazaro.xlam and check it" step. Live-verified end to end on this machine: installed silently to a test directory, confirmed `Application.AddIns` listed the add-in with `Installed=True` after a fresh Excel launch, then uninstalled and confirmed the registry entry and files were both removed cleanly, with no effect on any other `OPEN`-registered add-in.
- Registers a real Windows uninstall entry (Add/Remove Programs) that removes everything the installer placed, including the `OPEN` registry entry it added (and only that entry — any other add-in registered the same way is left untouched).

It does **not** attempt to flip the Trust Center checkbox — that one setting is specifically walled off by Microsoft from installer automation for individual, unmanaged users, on purpose (it's the setting a malicious installer would most want to flip silently), so no installer can script around it. It stays the one manual part, same doctrine as the VBA-project-locking step above: honest and irreducible rather than silently automated on a guess.

To build the installer: `& "$env:LOCALAPPDATA\Programs\Inno Setup 6\ISCC.exe" installer\Frazaro.iss` (or open the `.iss` in the Inno Setup IDE and press Compile) — requires `Frazaro.xlam` **and** `installer\version.iss` to already exist (run `VlaBuildAddin` first — it writes both). Output lands in `installer\output\FrazaroSetup.exe`, its `AppVersion`/`DisplayVersion` sourced from `VLA.VLA_RELEASE_VERSION` rather than the hand-typed `"1.0"` literal this project shipped with for its entire life until DI.3a (a real, confirmed finding — that literal was never once touched, because nothing forced a human to remember two places to update it). Then sign it: `installer\sign_installer.ps1` (see "Code signing" above).

**DI.3b, live-verified, install → upgrade → uninstall, not just built:** installed silently to a scratch test directory (`/DIR=` override) at `0.1.0` — `Application`'s own `OPEN` registry slot and the Windows Uninstall registry entry (`DisplayVersion 0.1.0`) both confirmed written. Rebuilt at `0.1.1` (`version.iss` bumped, same `AppId`) and reinstalled over the same location: exactly one `OPEN` slot afterward (no duplicate — `RegisterExcelAddin`'s existing-value check held), exactly one Uninstall registry entry, `DisplayVersion` correctly updated to `0.1.1`. Uninstalled: both the registry entry and the `OPEN` slot were gone afterward, and the install directory was removed completely. **A genuine, unrelated finding surfaced along the way:** this machine has Windows 11's Smart App Control **On**, which silently blocked launching the freshly-rebuilt (`0.1.1`) installer outright — a completely unsigned `.exe`, even one built minutes earlier by the same toolchain that just ran successfully at `0.1.0`, was refused with "An Application Control policy has blocked this file," no dialog, no prompt. Self-signing it first (`installer\sign_installer.ps1` — the DI.1 self-signed cert, no CA chain) was enough to let it run, even though the certificate itself is still reported as untrusted by the same OS. **Consequence, not yet acted on:** on a Smart App Control machine, distributing an *unsigned* rebuilt installer between releases may simply fail to launch for a user with no obvious explanation — a real argument, independent of DI.1's own SmartScreen reasoning, for signing the installer as a standard part of every release rather than an optional step.

### Standalone — for a managed machine, or when unsure

1. Copy `Frazaro.xlam` to the AddIns folder (`%AppData%\Microsoft\AddIns`) — or anywhere, and browse to it in the next step. If the build embedded `prelude.vla`/`english.vla` (see "Which download should I use?" above for verification status), this is the only file needed; otherwise also copy `prelude.vla` and `english.vla` into a `scripts` folder beside it (or beside the user's own workbook — see "Using it" below for how the vocabulary file is found).
2. Excel → File → Options → Add-ins → Manage: Excel Add-ins → Go… → check **Frazaro** (Browse… if needed) — or, once it's open once, click the ribbon's own **Register for Auto-Load** button instead, which does the same registry write without needing this dialog at all.
3. **Only if you intend to use Compile** (the export path): Trust Center (File → Options → Trust Center → Trust Center Settings → Macro Settings): enable macros, and check **"Trust access to the VBA project object model."** This is the one Office setting that lets a program's compiled VBA be written into a workbook, and it's the one step neither installation path can automate (see above). **Interpret needs neither of these** — it runs every program directly, in-process, with no VBProject access at all (IN.6/IN.9): a plain `.xlsx`, nothing injected, nothing to trust. This is the default runtime; Compile is the deliberate, opt-in export for a self-contained workbook or a performance-sensitive loop (see `BETA_ROADMAP.md`'s Interpreter/Emitter comparison table).
4. A **Frazaro** ribbon tab appears, plus the legacy **Frazaro** menu under the **Add-ins** tab — same commands either way.

**Protected View: an owner-caught failure mode, distinct from the Trust Center step above.** A first fresh-machine test of `Frazaro_Beta.xlam` hit *"This file type is not supported in Protected View"* and was worked around by adding the machine's desktop as a Trust Center Trusted Location — the exact onboarding friction this whole standalone path exists to avoid, and heavier than the problem needs. The cause is the file's Mark-of-the-Web (`Zone.Identifier`) tag, set by whatever transferred it (browser download, email attachment, zip extraction, some network/cloud-sync paths) — not signing, and not anything either `.xlam` distribution path controls once the file is already on disk. **The lighter fix:** right-click the file → Properties → check **Unblock** → OK (or `Unblock-File -Path Frazaro.xlam` in PowerShell) *before* opening it — one file, one time, no Trust Center change.

Reproducing it on a dev machine (a locally-built `.xlam` carries no MOTW tag on its own, so nothing triggers this without deliberately adding one):
```powershell
Set-Content -Path Frazaro.xlam -Stream Zone.Identifier -Value "[ZoneTransfer]`r`nZoneId=3"   # tag it, as if downloaded
Get-Content -Path Frazaro.xlam -Stream Zone.Identifier                                        # confirm the tag is there
Unblock-File -Path Frazaro.xlam                                                               # the fix
```
**Verification status, precisely:** the tag-add/tag-remove mechanics above are session-verified — adding the stream, reading it back, and `Unblock-File` clearing it were all confirmed live on a scratch copy. What that scratch test could *not* confirm without an actual Excel open (a GUI click-through, same methodology as DI.1's macro-trust states above): that a MOTW-tagged `.xlam` reproduces the identical modal on a second machine, and that `Unblock-File` alone — no Trusted Location — lets it open cleanly afterward. Next owner step: tag a scratch copy as above, confirm the modal, run `Unblock-File`, confirm a clean open.

**The installer path is immune to this specific failure, confirmed live, not assumed.** Signed `FrazaroSetup.exe` (DI.1's self-signed cert) was copied, tagged with `Zone.Identifier` `ZoneId=3` exactly as above — simulating a browser download of the installer itself — then run `/VERYSILENT` to a scratch `/DIR=`. Every extracted file (`Frazaro.xlam`, `english.vla`, `prelude.vla`) carried **no** `Zone.Identifier` stream afterward: Inno Setup's own extraction does not propagate the parent `.exe`'s MOTW tag to the files it writes, confirming the general Windows behavior for this specific installer rather than assuming it. Scratch install then uninstalled via its own `unins000.exe` and confirmed removed with no stray registry residue. **Net effect on the "two problematic options" framing:** the installer path was never actually a *second* instance of this problem — its only real friction is the separate `.exe`-execution-policy question already documented above (managed machines blocking downloaded `.exe`s), not Protected View. A pilot user on an unmanaged machine who can run the installer at all sidesteps this issue entirely; only the standalone `.xlam` path needs the Unblock step.

## Updating or removing the add-in (between builds)

**Update loop:** Add-ins dialog (File → Options → Add-ins → Manage: Excel Add-ins → Go…) → **untick Frazaro**. Unticking closes the add-in workbook — the ribbon leaves with the file, the close handler removes the menu, and Excel releases its lock on the `.xlam` — so you can overwrite it with the fresh build and re-tick, no Excel restart needed. **Full removal:** untick, close Excel, delete or move the `.xlam` (the Inno Setup uninstaller does this, plus the `scripts\` companions and the `OPEN` registry entry, automatically), reopen Excel and open the Add-ins dialog — Excel asks whether to drop the now-missing entry from the list; say yes (the question only appears once the file is gone). **One trap, now reachable two ways:** installing by browsing *directly to the build output* beside the dev workbook means a ticked add-in holds a lock exactly where `VlaBuildAddin` wants to save — install from a copied location (the installer's `%AppData%\Frazaro` does this automatically), or untick before building. **Register for Auto-Load creates the identical trap if pointed at the build output itself** — owner-caught live: registering `...\Beta\Frazaro.xlam` directly means *every* Excel session auto-loads and locks that exact file, not just ones where you deliberately opened it, so the next `VlaBuildAddin` run fails trying to overwrite a file Excel is holding open. Same fix, same reason: register a copied location instead of the build output, or unregister first (`?VLA_IDE.VlaUnregisterAutoLoad("<path>")` from the Immediate window — no ribbon button for this yet, see "Which download should I use?" above) before rebuilding.

**Three corrections along the way, every one owner-caught, the last one caught by a real click-through rather than any test harness — worth reading in order, because each fix answered the previous challenge and then exposed the next one.**

1. First version showed a "delete this file by hand" message for the standalone case. Correctly called out as not a real answer for a non-technical user asked to find and delete a file in an unfamiliar folder — changed to genuinely delete the file itself, via a detached PowerShell process (not this workbook's own code, sidestepping the untested question of whether code can delete the file it's currently running from).
2. That process waited a fixed 3 seconds, then deleted once. Correctly challenged as fragile — a fixed delay assumes Excel's close finishes in time, and anything that slows it down (a loaded machine, antivirus scanning the file, a cloud-sync client, `Workbook_BeforeClose`'s own cleanup work) could outrun a guessed number. Changed to a retry loop: every 500ms for up to 10 seconds, live-tested against a file held under an exclusive lock for 2 full seconds with the retry already running — it failed silently and kept trying until the lock released, then succeeded immediately.
3. Still broken, found by deliberately trying to break it: the retry process launched from the same code that showed a *second*, purely informational dialog afterward — and deliberately pausing 30+ seconds on that dialog let the entire 10-second retry window expire while the workbook was still open blocking every attempt, long before the dialog was even dismissed. The window was counting down from the wrong moment. Fixed structurally, not by widening the window again: the informational dialog is gone (its content folded into the one confirm dialog, shown *before* the user commits), and the retry process now launches from inside the deferred-close step itself, with nothing blocking between "confirmed" and "closing, then deleting."

**What to confirm now:** the confirm dialog carries all the information (including the `scripts`-folder note, if present) and **No** does nothing; clicking **Yes** on a standalone copy closes it with no further dialog, and the file is actually gone a few seconds later regardless of how long you take to read anything beforehand; the exe-installed case correctly launches the real uninstaller instead.

### Platforms

**Interpret (the default runtime) needs no VBProject access**, so it is not architecturally Windows-only the way Compile is — but it has only been live-verified on Windows so far; Mac Excel support (`EN.6`) is a real, un-ratified item, not a shipped claim. **Compile is Windows-only**: running a program generates VBA into the workbook via VBProject automation, which Mac Excel does not permit — Compile refuses with one clear sentence there rather than failing silently. Paths already use `Application.PathSeparator` and the keyed-memory helpers already carry a no-Scripting fallback, so the codebase itself carries no known Windows-only assumption below the VBProject boundary; what's missing is a live Mac run to confirm it.

## Using it (each program)

1. Open (or create) a workbook and **save it as `.xlsm`** if you intend to use Compile (macro-enabled — generated programs live in the workbook's own VBA project). Interpret works against a plain `.xlsx` with nothing injected.
2. Put `english.vla` in a `scripts` folder next to the workbook (or directly beside it; the add-in also falls back to its own `scripts` folder or its own location, so a shared vocabulary can ship alongside the `.xlam` — see `VLA_IDE.IdeVocabPath`'s four-candidate search order). `prelude.vla` always resolves beside the add-in itself, never the user's workbook (`VLA.PreludeVlaPath`) — every compile or interpret needs it.
3. The **Frazaro** ribbon tab (or the legacy Add-ins-tab menu) → **Set Up Workspace**. Write the program in column A of the *Frazaro* sheet — one sentence per row, blank rows end blocks, `#` starts a comment. A workbook can hold **several programs**: **Add Program** creates additional `Frazaro (<name>)` sheets with the same buttons. Every command binds to the program whose sheet you use it from, each program compiles to its own module (`Frazaro_EN_Sheet` for the default, `Frazaro_EN_<name>` for named ones), and Run/Undo are scoped per program.
4. **Check Instructions** validates without running (green OK per row; the first problem in red beside its sentence). **Interpret Instructions** / **Interpret and Trace** run the program directly, no VBProject access, no trust setting needed — this is the default path. **Compile Instructions** / **Compile and Trace** generate real VBA into the workbook and run it — needs the Trust Center setting above, and produces a workbook that keeps running after Frazaro is uninstalled (IN.9's export path). **Show Compiled VBA** shows what Compile would generate without running it. **Undo Last Run** restores the sheets the last run touched. **Known Sentences** lists every sentence shape the vocabulary understands, with worked examples.

## What Compile puts into your workbook

Compiling writes **two modules** into the workbook's own VBA project: `Frazaro_EN_<program>` (the compiled program) and `Frazaro_EN_Runtime` (the small helper library the generated code calls — colors, counts, lookups, mail drafts). `Frazaro_EN_Runtime` is rewritten on every Compile, so helper fixes propagate automatically. The payoff: **a workbook that has been Compiled is self-contained** — its macros keep working on machines where Frazaro isn't installed (the "no new runtime" promise made literal). Interpret has no equivalent artifact — nothing is written to the workbook at all; the program only runs while Frazaro's add-in is loaded.

**Whose code is that, legally?** Yours. `Frazaro_EN_Runtime` carries a BSD Zero Clause (0BSD) notice in its own header — it travels with the module, so an auditor opening the workbook sees the terms without leaving it — and `Frazaro_EN_<program>` is generated output, which `OUTPUT-EXCEPTION.md` in the repository places outside every Frazaro licence. A workbook that has been Compiled can be emailed, archived, or handed to a consultant with no licence obligation of any kind (`SIG.0`).

## The feedback loop

Sentences Check can't understand are logged to a hidden sheet inside the user's workbook (local only, capped at the newest thousand). The **Copy Feedback** button exports the log — with engine version, sentence count, and program path — as one clipboard block for emailing to the vocabulary maintainer. This corpus of what people *actually tried to say* is the input that should rank all vocabulary work; ask pilot users to send it weekly. `EnglishIdeClearLog` (Immediate window) resets it.

## What Undo covers (honestly)

Snapshots are real sheet copies, so Undo restores *state* — including bringing back a sheet the run (or you) deleted, something Excel's own undo can't do — and removing a sheet the run created: named targets that don't exist at snapshot time leave a tombstone marker, and Undo deletes the sheet with its marker ("the state before the last run" is a state where it did not exist). Undo remains one run deep **per program**: each program's snapshots wear its own prefix, so undoing one program never touches another's history — but two programs writing the same sheet still interleave honestly. Before each Run, the workspace sheet (*Output*, or the sheet a `Work on sheet …` declaration names) plus any sheet named after the word "sheet" in the program, and any sheet reached by a qualified reference (`Data!B2`, `'Q1 Data'!A1`), is snapshotted (as very-hidden `VLAu_*` sheets), and Undo restores those snapshots. Not covered: sheets reached in ways the scan can't see, other workbooks, and non-sheet state (e.g. saved files). Sheets whose names are too long to snapshot are skipped with a note in the Immediate window.

## Troubleshooting

**The Frazaro ribbon shows but Frazaro isn't in the Add-ins list** → the `.xlam` is *open* (double-clicked, or left open from the locking step) rather than *registered*: an opened add-in loads invisibly — ribbon and menu appear — but the Manage: Excel Add-ins list shows only registered add-ins, and an open-but-unregistered add-in silently unloads when Excel closes. Confirm with Alt+F11 (`VlaTools (Frazaro.xlam)` in the Project Explorer). Register it via Browse… in the dialog, or close it from the Immediate window: `Workbooks("Frazaro.xlam").Close False`. **Developer caution:** the `.xlam` loaded beside the dev workbook means two copies of the code coexist — ribbon clicks run the xlam's copy, workspace buttons made by the dev session run the dev copy. Develop with the xlam closed; test the xlam without leaning on dev-created buttons.

"This file type is not supported in Protected View" → the `.xlam` carries a Mark-of-the-Web tag from however it was transferred; not a signing or Trust Center problem (see "Protected View / Mark-of-the-Web" under Code signing, and the Standalone section's fix, above) — right-click → Properties → **Unblock**, or `Unblock-File`, rather than adding a Trusted Location.

"Programmatic access to Visual Basic Project is not trusted" → the Trust Center checkbox from step 3 above, needed only for Compile — switch to Interpret if you don't need a self-contained exported workbook, or enable the checkbox if you do. "prelude.vla not found" / "Vocabulary file not found" → the message names the exact paths it looked for; put the file at one of them (see "Using it" above for the search order). A compile error at a `vla…` helper in `Frazaro_EN_<program>` → the installed add-in predates the `Frazaro_EN_Runtime` naming (IO.6); rebuild with `VlaBuildAddin` and update the installed copy. No Frazaro ribbon tab after installing → the build's ribbon injection didn't run; re-run `VlaBuildAddin` (watch its report line), or run the printed `VlaRibbonInject.ps1` by hand — meanwhile every command is on the Add-ins-tab menu. A silent stop with no message on a developer machine → check VBE Tools → Options → General → Error Trapping is *Break on Unhandled Errors*.
