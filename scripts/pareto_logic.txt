# pareto_logic.txt — the query-and-logic corpus

**What this file is.** The specification corpus for the query family's
grammar (`G-PROLOG` first, `G-DATALOG`'s second wave, `G-SQL`, `G-OPTIMIZE`):
real Prolog-shaped business tasks, each with the question a manager would
actually ask, the canonical program it must become, a tiny Table set to prove
it on, and the answer that program gives. It is `pareto.txt`'s sibling and
obeys the same two laws: no rule ships from here without `test:` proofs from
real output, and SD-7 — no grammar without a sentence that needs it. This
file supplies the sentences.

**Why its own file, not a `pareto.txt` section.** A pareto entry is one line:
`id | surface | target operation`, where the target is a COM call. A query
entry cannot be one line. Its target is a program (a rule set plus a query,
often five clauses), and that program means nothing without the Tables it
runs over, so every entry carries a fixture and a measured answer. The
target is engine text rather than an Excel operation, and the corpus's job
is also different: pareto predicts single operations, while this file
has to show that a small set of sentence frames composes into all of
these programs. Folding it into pareto would break pareto's own grammar.

**What the manager's question is NOT.** It is not the sentence Frazaro
accepts. SD-16 makes the phrasebook's pattern language the only sentence
grammar, so a free question such as "who can cover the night shift" is the
*specimen*, and the controlled sentences that reach it come from the frames
listed in each entry (the frame key below). Those spellings are decided in
`G-PROLOG`'s scope (`docs/BETA_ROADMAP1.md`), not here.

---

## How to read an entry

```
  id               priority  engine   frames
    asks     the question, as a manager would put it
    program  the canonical program text
    on       the fixture (below)
    answers  what the cell holds, measured          [steps, depth]
```

**Markers**, pareto's own plus two:

| | meaning |
|---|---|
| `!` | needs a **Tier-2 runtime helper** |
| `~` | needs a **grammar feature first** |
| `?` | **semantic decision required**; the note says what |
| `#` | **over the step ceiling today** — answers only after `PROLOG.28` |
| `x` | **not this engine's** — routed or refused, never faked |
| `o` | **`OPTIMIZE`'s, unbuilt** — a hand-derived answer key, re-derived by `tools/optimize01_corpus.ps1`; §17 only |

**Engines.** `P` PROLOG · `D` DATALOG · `P|D` the shared Horn fragment,
either engine gives the same set · `Q` SQL · `O` OPTIMIZE (unbuilt).

**Priorities**, pareto's: `P0` a beta without it looks unfinished · `P1`
common by month two · `P2` real but narrower. Breadth beats depth.

**How the answers were measured.** Every `P` program below was run through
the transliteration `PROLOG.22` built (a PowerShell model of `VLA_Prolog`'s
parse and solve, its tables read from the VBA source), extended by one arm
for `length`. **Control first:** the model reproduces 568 of `TestDSLs`'
live-verified assertions with 0 failures, 265 counted as gaps and never as
passes; a mutation of the `length` arm turns 7 red. Steps are what
`PROLOG_MAX_STEPS` (120) is charged; depth is the deepest nesting of
`SolveGoalList` frames, the thing the ceiling exists to protect. Where a
program needs more than 120 steps it is run a second time with work
uncapped and depth capped at 60, and both numbers are given. `D`, `Q` and
`O` programs are not measured here; there is no DATALOG transliteration.
**No answer below has been seen in a cell yet.** `O` entries (§17) carry
no program at all: their rules are plain English, and their keys were
derived by hand and re-derived by enumeration, before the engine exists.

## The frame key

Spelling-independent names for the sentence frames the corpus needs; the
roadmap's scope gives each its English.

*Reading a Table* — the only frames that see rows:

| frame | clause it writes |
|---|---|
| `T2` pair | `(rule (r X Y) (t (a X) (b Y)))` |
| `T1` set | `(rule (s X) (t (a X)))` |
| `TW` pair with a row condition | `(rule (r X Y) (t (a X) (b Y) (c V)) (>= V 3))`, or `(c X)` twice for a same-row match |
| `J` join | `(rule (r X Y) (t1 (a X) (c V) (e P)) (t2 (b Y) (d V) (f Q)) (>= P Q))` — one match pair, at most one comparison |
| `F` fact | `(fact (r "Bob" "Carol"))` |

*Composing named relations* — one clause each, never a row:

| frame | clause it writes |
|---|---|
| `ALSO` rename, and union by repetition | `(rule (r X Y) (a X Y))` |
| `AND` | `(rule (r X Y) (a X Y) (b X Y))` |
| `BUTNOT` | `(rule (r X Y) (a X Y) (not (b X Y)))` |
| `THEN` composition | `(rule (r X Z) (a X Y) (b Y Z))` |
| `CONV` converse | `(rule (r X Y) (a Y X))` |
| `CLOS` directly or not | `(rule (r X Y) (a X Y)) (rule (r X Y) (a X Z) (r Z Y))` |
| `CMP` compare through values | `(rule (r X Y) (a X V) (b Y W) (>= V W))`; `matching` shares `V` |
| `SEL` select by a constant | `(rule (s X) (a X V) (>= V 10000))` |
| `PROJ` anyone who | `(rule (s X) (a X Y))` |
| `IF` first match (P only) | `(rule (r X T) ... (if C1 (= T "Gold") (if C2 ...)))` |
| `TEXT` prefix, contains (P only) | `(rule (s X) (a X V) (sub-atom V 0 4 After "GL-4"))` |

*Asking* — the codomain; every one writes only the `(query ...)`, plus
helper rules named `vla-*` where the shape needs one:

`WHO` subject unknown · `WHAT` object unknown · `WHETHER` ground, a TRUE or
FALSE · `PAIRS` both unknown · `COUNT` · `LIST` in one cell · `NONE` /
`EVERY` · `ONLY` · `ANY` one (cut) · `EACH` per group.

*Placement* is not a frame: every authoring sentence ends "in cell …" and
every question names its rules range, its Tables and its cell.

## Fixtures

Tiny on purpose, and each one hides the trap its section is about.

```
STAFFING  Shifts(Shift, Needs, MinLevel)  Staff(Name, Cert, Level)       Leave(Name, Shift)
          Day      First-aid 1            Ann First-aid 3                 Di  Night
          Night    Forklift  2            Bob Forklift  3                 Ann Weekend
          Weekend  First-aid 3            Bob First-aid 1
                                          Cy  Forklift  1
                                          Di  Forklift  3
                                          Ed  First-aid 2
  (the trap: Bob's LEVEL belongs to each certification row, and his only
   First-aid row is level 1 — a level taken from his Forklift row would
   wrongly clear him for Weekend.)

          Invoices(Invoice, Submitter, Amount): INV-1 Eve 1500 · INV-2 Eve 8000 · INV-3 Frank 30000
          Delegations(From, To): Alice Carol

ACCESS    UserRoles(User, Role): ann analyst · bob admin · cy viewer
          RoleInherits(Role, Parent): admin analyst · analyst viewer
          RolePerms(Role, Perm): viewer read · analyst export · admin delete

COI       Expenses(Expense, Submitter, Approver): E1 Bob Bob · E2 Carol Alice · E3 Dave Eve
          Relatives(A, B): Eve Dave

SCHEDULE  Assignments(Person, Shift): Ann S1 · Ann S2 · Bob S3
          ShiftTimes(Shift, Day, Start, End): S1 Mon 8 16 · S2 Mon 14 22 · S3 Tue 8 16

          Approvals(Bill, Approver): B1 Alice
          Preferred(Vendor): Beta

          Staff of 5, 10, 15, 20 people over five shifts
```

The slice-1 knowledge base, `KB1`, is used throughout §1 and §14:

```
(rule (qualified-for X Y) (staff (name X) (cert V) (level P))
                          (shifts (shift Y) (needs V) (minlevel Q)) (>= P Q))
(rule (on-leave-for X Y) (leave (name X) (shift Y)))
(rule (can-cover X Y) (qualified-for X Y) (not (on-leave-for X Y)))
```

## 1. Eligibility and policy — P0

*The README's own specimen, and the section that decides the composition
model: its Level is an attribute of a (person, certification) row, so no
chain of two-place relations can carry it (see `elig-lossy`).*

```
elig-readme          P0  P|D   (one rule, not frames)
  asks     Who can cover which shift?  (the README rule, verbatim)
  program  (rule (can-cover Shift Who) (shifts (shift Shift) (needs Cert) (minlevel Min))
             (staff (name Who) (cert Cert) (level Level)) (>= Level Min)
             (not (leave (name Who) (shift Shift))))
           (query (can-cover Shift Who))
  on       STAFFING
  answers  Shift|Who: Day Ann · Day Bob · Day Ed · Night Bob                  [49, 7]

elig-who             P0  P|D   J T2 BUTNOT · WHO
  asks     Who can cover the night shift?
  program  KB1 (query (can-cover Who "Night"))
  answers  Who: Bob                                                         [37, 9]

elig-who-day         P0  P|D   J T2 BUTNOT · WHO
  asks     Who can cover the day shift?
  program  KB1 (query (can-cover Who "Day"))
  answers  Who: Ann · Bob · Ed                                              [41, 8]

elig-who-none        P0  P|D   J T2 BUTNOT · WHO
  asks     Who can cover the weekend?
  program  KB1 (query (can-cover Who "Weekend"))
  answers  Who: (the header, nothing under it)                              [33, 9]

elig-whether         P0  P|D   J T2 BUTNOT · WHETHER
  asks     Can Bob cover the night shift?  Can Di?  Can Bob cover the weekend?
  program  KB1 (query (can-cover "Bob" "Night"))   ... "Di" "Night" ... "Bob" "Weekend"
  answers  TRUE · FALSE (on leave) · FALSE (the trap, answered right)       [19 · 16 · 15]

elig-what            P0  P|D   J T2 BUTNOT · WHAT
  asks     Which shifts can Bob cover?
  program  KB1 (query (can-cover "Bob" What))
  answers  What: Night · Day                                                [25, 8]

elig-pairs           P1  P|D   J T2 BUTNOT · PAIRS
  asks     Who can cover what?
  program  KB1 (query (can-cover Who Which))
  answers  Who|Which: Ann Day · Bob Night · Bob Day · Ed Day                [59, 9]

elig-lossy        ?  —   —     T2 T2 T2 T2 THEN CMP BUTNOT  (REJECTED)
  asks     The same policy built only from two-place relations:
           holds(Name,Cert), needs(Shift,Cert), level-of(Name,Level),
           asks-for(Shift,MinLevel), then qualified-for and cleared-for.
  answers  Weekend: Bob — WRONG (his Forklift level cleared his First-aid)  [85, 16]
           Day: Ann · Bob · Bob · Ed — a duplicate                          [93, 15]
  note     The reason the scope has a J frame. A ternary row is not the join
           of its binary projections unless the attribute depends on the
           person alone; here it depends on the person AND the certification.
```

## 2. Org charts and reporting lines — P0

*SD-19's founding pair for this family: "reports to" directly and "reports
to, directly or not" are neighbouring questions, and each sentence names
which. Transitive closure blows the step ceiling on six rows.*

```
org-direct           P0  P|D   T2 · WHO
  asks     Who reports to Alice?
  program  (rule (reports-to X Y) (reports (employee X) (manager Y)))
           (query (reports-to Who "Alice"))
  on       ORG
  answers  Who: Bob · Carol                                                 [7, 3]

org-under          # P0  D     T2 CLOS · WHO
  asks     Who reports to Alice, directly or not?
  program  ... (rule (under X Y) (reports-to X Y))
               (rule (under X Y) (reports-to X Z) (under Z Y))
           (query (under Who "Alice"))
  answers  today: prolog-step-ceiling, blaming "a rule that recurses without
           ever reaching a base case" — a wrong explanation of a correct rule
           uncapped: Who: Bob · Carol · Dave · Eve · Frank                  [176, 12]
  note     DATALOG answers this today (G-DATALOG's datalog-chain-place).

org-above            P0  P|D   T2 CLOS · WHAT
  asks     Who is above Eve?
  program  ... (query (under "Eve" Who))
  answers  Who: Dave · Bob · Alice                                          [64, 12]

org-skip             P1  P|D   T2 THEN · WHO
  asks     Who are Alice's skip-level reports?
  program  ... (rule (skip-level X Y) (reports-to X Z) (reports-to Z Y))
           (query (skip-level Who "Alice"))
  answers  Who: Dave · Frank                                                [50, 6]

org-top              P0  P|D   T1 T2 PROJ BUTNOT · WHO
  asks     Who has no manager?
  program  ... (rule (person X) (roster (name X))) (rule (has-manager X) (reports-to X Y))
               (rule (top X) (person X) (not (has-manager X)))
           (query (top Who))
  on       ORG (Reports and Roster)
  answers  Who: Alice · Hal                                                 [82, 8]

org-managers         P1  P|D   T2 PROJ · WHO   (set, not bag)
  asks     Who manages anyone?
  program  ... (rule (manager Y) (reports-to X Y)) (query (manager Who))
  answers  Who: Alice · Alice · Bob · Dave · Carol · Hal                    [8, 4]
  note     A "who" answer must be a SET: Alice appears once per report. The
           duplicate is measured, not hypothetical (also pre-blocked, sched-clash).

org-span             P1  P|D   T2 · COUNT
  asks     How many people report to Alice directly?
  program  ... (rule (vla-count N) (findall X (reports-to X "Alice") B) (length B N))
           (query (vla-count N))
  answers  N: 2                                                             [10, 5]
  note     findall counts derivations, not people; see COUNT in §15.

org-peers            P1  P     T2 · WHAT  (inequality)
  asks     Who are Bob's peers?
  program  ... (rule (peer X Y) (reports-to X M) (reports-to Y M) (\= X Y))
           (query (peer "Bob" Who))
  answers  Who: Carol                                                       [17, 7]
```

## 3. Approval chains and delegation of authority — P0

*Functional attributes (one Limit per approver, one Amount per invoice), so
here two-place relations ARE lossless and compose freely.*

```
appr-who             P0  P|D   T2 CLOS THEN CMP · WHO
  asks     Who can approve INV-2?  (anyone above the submitter whose limit covers it)
  program  ORG's under, plus
           (rule (limit-of X L) (limits (approver X) (limit L)))
           (rule (submitted-by I X) (invoices (invoice I) (submitter X)))
           (rule (amount-of I A) (invoices (invoice I) (amount A)))
           (rule (above-submitter Y I) (submitted-by I X) (under X Y))
           (rule (can-approve Y I) (above-submitter Y I) (limit-of Y L) (amount-of I A) (>= L A))
           (query (can-approve Who "INV-2"))
  on       APPROVAL
  answers  Who: Bob · Alice                                                 [100, 19]
           INV-3: Alice                                                     [74, 16]

appr-delegated     # P0  P|D   ... ALSO · WHO
  asks     Who can approve INV-3, counting delegations?
  program  ... (rule (delegates X Y) (delegations (from X) (to Y)))
               (rule (may-approve Y I) (can-approve Y I))
               (rule (may-approve Y I) (delegates X Y) (can-approve X I))
           (query (may-approve Who "INV-3"))
  answers  uncapped: Who: Alice · Carol                                     [142, 19]
  note     Union is two sentences with one head (ALSO twice). A delegation
           cycle would make CLOS-over-delegation non-terminating in PROLOG.
```

## 4. Access control and role inheritance — P0

```
acc-can              P0  P|D   T2 CLOS THEN ALSO · WHAT
  asks     What can bob do?
  program  (rule (has-role U R) (userroles (user U) (role R)))
           (rule (inherits R P) (roleinherits (role R) (parent P)))
           (rule (inherits-any R P) (inherits R P))
           (rule (inherits-any R P) (inherits R Z) (inherits-any Z P))
           (rule (role-of U R) (has-role U R))
           (rule (role-of U P) (has-role U R) (inherits-any R P))
           (rule (perm R X) (roleperms (role R) (perm X)))
           (rule (can U X) (role-of U R) (perm R X))
           (query (can "bob" What))
  on       ACCESS
  answers  What: delete · export · read                                     [47, 13]

acc-whether          P0  P|D   same · WHETHER
  asks     Can ann delete?
  answers  FALSE                                                            [35, 10]

acc-who              P0  P|D   same · WHO
  asks     Who can export?
  answers  Who: ann · bob                                                   [83, 13]
  note     role-of must be right-recursive: `(role-of U P) (role-of U R) (inherits R P)`
           loops in PROLOG. CLOS writes the right-recursive form, always.
```

## 8. Classification and tiering — P0

```
tier-first           P0  P     IF · PAIRS
  asks     Which tier is each customer?  (Gold from 10000, Silver from 5000, else Bronze)
  program  (rule (tier C T) (customers (customer C) (spend S))
             (if (>= S 10000) (= T "Gold") (if (>= S 5000) (= T "Silver") (= T "Bronze"))))
           (query (tier Who Tier))
  on       TIERS
  answers  Who|Tier: Acme Gold · Beta Silver · Cafe Bronze                  [19, 8]
  note  ?  Measured by G-PROLOG slice 5's scoping (2026-09-14). First match is
           per ROW here: with a second Customers row Acme 900, Acme is Gold AND
           Bronze. DATALOG refuses (if ...) as nesting. Decided: first match is
           "otherwise" in one sentence, compiled per key to each branch's own
           conditions plus (not ...) of every earlier branch's generated guard,
           which answered Acme Gold, Beta Silver, Cafe Bronze in both engines,
           one tier per customer whatever its rows. Or by repetition without
           the negations makes Acme Gold, Silver and Bronze, silently. Said
           since G-PROLOG slice 5: a customer has-tier "Gold" if ..., otherwise
           "Silver" if ..., otherwise "Bronze" if Customers lists the customer
           as Customer.

tier-strata          P0  P|D   TW SEL BUTNOT · WHO
  asks     Who is Silver?  (the DATALOG-shaped spelling: a band, minus the band above)
  program  (rule (gold C) (customers (customer C) (spend S)) (>= S 10000))
           (rule (silver C) (customers (customer C) (spend S)) (>= S 5000) (not (gold C)))
           (query (silver Who))
  answers  Who: Beta                                                        [19, 8]
```

## 12. Routes and connectivity — P1

```
routes-reach       x P1  D     T2 CLOS · WHETHER
```

## 17. Search and optimisation — OPTIMIZE's corpus

*Not a logic query. Every entry here asks for a DECISION, which of the ways
things could be is best, and none of the other three engines can make one.
Grown from one entry to twenty by `OPTIMIZE.0.1` (2026-09-19), across the
five segments of Contemplation 8 (compliance assignments, shift rosters,
event seating, configuration and quoting, timetabling), before any of
`VLA_Optimize.bas` exists. Every fixture is tiny, and every key was written
by hand first and then re-derived by `tools/optimize01_corpus.ps1`, which
walks every candidate world, checks every rule on each, and exits non-zero on
any disagreement with the key printed here. `tools/optimize01_lp.ps1` exports
each entry for clingo, the dev-only oracle the owner runs by hand.*

**How an OPTIMIZE entry is written.** There is no program to show yet, so:

```
  id                          marker priority engine   shapes
    asks     the question, as a manager would put it
    on       the fixture, inline
    rules    one rule a line, in plain English, tagged with its kind
    key      satisfiable or not · valid worlds of the candidates · the optimum,
             in the objective's order, and how many worlds reach it
    why      for "no world": the reason, in the words the answer should use
    clingo   the oracle's check: done, or pending until the owner runs it
    note     how the key was derived by hand
```

**The rules are English on purpose, and no line below is a spelling.** The
bracketed kind is the roadmap's own name for the concept: `[choice]`,
`[constraint]`, `[derived]`, `[objective]`, `[kept]`, `[budget]`, `[status]`.
It is illustrative, not a keyword. The forms' spellings are `OPTIMIZE.1`'s to
choose, under the long-term-first rule for parsing decisions, and the
sentences are `G-OPTIMIZE`'s. Both are judged against these lines: a spelling
that cannot say one of them plainly is the wrong spelling.

**Shapes**, neutral names for coverage only: `ONE` / `EXACT-k` (exactly one
or k chosen per group) · `OPTIONAL` (zero or one) · `AT-MOST` (a cap counted
over chosen rows) · `APART` / `TOGETHER` (two named rows never / always in
one group) · `IN-A-ROW` (a pair relation over consecutive groups) · `POOL`
(eligibility narrows the choice) · `REQUIRES` / `EXCLUDES` · `SUM-CAP` (a
weighted sum under a bound) · `DERIVED` (a rule over chosen rows) · `MIN` /
`MAX` / `WEIGHTED` (the objective) · `KEEP` · `CHECK` (no choice at all) ·
`COUNT` (how many worlds) · `NONE-COUNT` / `NONE-LOCAL` (no world, by
counting or by a conflict between named rules).

**What a key says.** A *candidate* is one way of making every choice before
any rule applies: a pair of people for each shift, a table for each guest. A
*valid world* is a candidate that breaks no constraint. The *optimum* is the
best objective value among the valid worlds, in the order the objective
states, and "N worlds reach it" is how many tie there. That is the number
`OPTIMIZE`'s Table-order tie-break (decision 2) must reduce to one answer.
"No world" is a first-class answer (`OPTIMIZE.2`), and each one's `why` line
is the sentence that answer should say. Four of those are by counting,
demand over capacity, which `OPTIMIZE.2`'s pre-checks answer by arithmetic
before any search.

**What the roster costs to ground, measured live 2026-09-19** (`OPTIMIZE.0`,
Excel 16.0 64-bit, one machine). OPTIMIZE does not exist yet, so each
constraint the roster needs was written as a `DATALOG` rule whose rows ARE
its ground instances. The fixtures are closed forms (`tools/VLA_DiagO0.bas`,
`O0Fixture`), and every answer was checked row by row and re-derived by
enumeration (`tools/optimize0_expected.ps1`). The reference roster: 50 people,
4 weeks, 3 shifts a day, 10 per shift (a tightness of 0.84).

| constraint | written as | largest size run | ground rows | seconds |
|---|---|---|---|---|
| the pool (anyone, any shift, not on leave) | a join and a `not` | 50 × 4 weeks | 3,600 | 0.16 |
| every shift's count | a native counter | 50 × 4 | 84 | 0.68 |
| every person-week's count | a native counter | 50 × 4 | 200 | 0.69 |
| never two in a row | a pair relation | 50 × 4 | 4,150 | 2.44 |
| at most 2 per shift | triples | 20 × 4 | 95,760 | 10.9 |
| at most 3 a week | 4-subsets | 10 × 1 | 59,850 | 17.3 |
| at most 5 a week | 6-subsets | one person-week | 54,264 | 17.6 |

Written as native counters, every rule of the reference roster grounds in
under a second (the pairs in 2.4 s). Written as combinations, the same rules
stop at toy sizes: 39× the counters' cost for "at most 2 per shift", about
5,000× for "at most 5 a week". At the reference roster they come to 1.6
million and 10.9 million rows, which is why `G-OPTIMIZE` may only ever write
the counter. **The toy's answer, for the corpus to come:** 5 people, 7
shifts, exactly 2 per shift, never two in a row has **7,290** valid worlds
(10 × 3^6) out of 10,000,000 candidates, by hand and by exhaustive search.
Two fixtures provably have no schedule: 5 people (one senior for seven
nights), and 10 people with the loose needs (63 slots a week, capacity 50).
**The answer key, from clingo** (a dev-only oracle, run by hand, never
shipped):
- the toy's 7,290 models;
- 10 people × 1 week: the proven optimum is overtime 0, 24 changes;
- 20 × 1: best found overtime 0, 92 changes, not proven;
- the reference roster: overtime 0, with between 236 and 1,486 changes, the
  optimum unknown after 10 minutes.

clingo proved the senior shortage at once, but could not prove the counting
one (63 against 50) in three minutes. That answer rests on the arithmetic.

## 18. Scale — why none of this survives a real Table today

```
scale-scan         # —   P     one Table, one question
  program  (query (big (name X) (n 7)))
  answers  119 rows: 119 steps · 120: 120 · 121: REFUSED · 200: REFUSED · 1000: REFUSED
           uncapped, 1000 rows: 1000 steps, depth 2

scale-join         # —   P     KB1, five shifts
  answers  5 staff: 45 · 10 staff: 84 · 15 staff: REFUSED (127) · 20 staff: REFUSED (170)
           depth 8 throughout
```

Every candidate a query tries costs one step, so work grows with the
Tables. Depth grows only with the proof, and the recursion that
`PROLOG_MAX_STEPS` was introduced to stop is depth. Across this whole
corpus the deepest terminating query needs **19** frames. Work reaches
1,000 on a plain scan, and passes 120 in six entries whose Tables have
fewer than ten rows each (`org-under`, `appr-delegated`, `bom-up`,
`none-covered`, `every-covered`, `count-each`); the two that pass it
because they never terminate (`lineage-selfname`, `routes-reach`) are the
depth case, the one the cap was built for. The one cap does two jobs, and when the work
runs out the refusal blames the user's rule for recursing, which is false.
That is `PROLOG.28`.

**DATALOG, measured live 2026-09-18** (`DATALOG.12`, six live passes, one
machine: Excel 16.0 64-bit). These are timings of the questions this corpus
already holds, written by the grammar itself — no new entries, so the counts
below are unchanged.

| shape | ms per row | measured |
|---|---|---|
| a scan | 2.55 | 100 rows 0.27s · 1,000 2.25s · 10,000 25.5s |
| a join (`can-cover`, three Tables) | 3.96 | 3,000 rows 11.9s |
| `count` per group (101 groups) | 2.54 | 3,000 7.6s |
| `textjoin` per group (11 groups) | 2.33 | 3,000 7.0s |
| `not` through a projection | 2.71 | 3,000 7.8s |
| "otherwise", five rules over one Table | 13.5 | 300 4.0s; 1,000 past the guard |
| closure, wide org (ten reports each) | 15–18 | 100 1.5s · 300 5.5s |
| closure, one chain | 216 | 100 links 21.6s |

Where `PROLOG` REFUSED a 121-row scan on its step ceiling, `DATALOG` answers
every one of these correctly at every size, and `MAX_ROUNDS` is never
approached: what stops it is time, not a budget. Four of the shapes sit in
one band of 2.3–4.0 ms a row, because the shape barely matters and the row
count does — 84% of that is one guard clause in `VLA_Runtime.bas`, asked once
per dictionary call (`DATALOG.13`). The closure's much larger cost is its
own question: every pair is built before the question narrows, and every
fixpoint round re-filters each relation in full (`DATALOG.14`). Recalculating
after one cell changes costs what the first answer cost, since nothing is
cached; a cell the question does not read costs nothing, since `DATALOG` is
not volatile.

**After `DATALOG.13`, measured live 2026-09-18** (same machine, same eight
programs, same expected answers). The guard clause now asks `TypeOf` rather
than `TypeName`, and every shape got five to ten times faster with every
answer unchanged:

| shape | ms per row | measured |
|---|---|---|
| a scan | 0.38 | 100 rows 0.06s · 1,000 0.38s · 10,000 3.8s |
| a join (`can-cover`, three Tables) | 0.68 | 3,000 rows 2.0s |
| `count` per group (101 groups) | 0.38 | 3,000 1.1s |
| `textjoin` per group (11 groups) | 0.38 | 3,000 1.1s |
| `not` through a projection | 0.50 | 3,000 1.5s |
| "otherwise", five rules over one Table | 1.29 | 300 0.41s · 3,000 3.9s |
| closure, wide org (ten reports each) | 3.3–3.8 | 300 1.0s · 1,000 3.3s · 3,000 11.3s |
| closure, one chain | 41 | 100 links 4.1s; 250 past the guard |

The one-Table shapes now share one figure, 0.38 ms a row, and most of that is
two dictionaries created per tuple. "Otherwise" gained most and no longer
grows faster than its rows at these sizes. The closures gained least, because
more of their time is the pair-building and rescanning that `DATALOG.14` is
about. A 100,000-row scan projects to about 38s, still past the 10s limit.
